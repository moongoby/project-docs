**날짜**: 2026-02-26
**대상 문서**: 백억이 V3.0 마스터 플랜 개정판 (데이터 퍼스트 전략)
**검토 방법**: DB 실측 교차검증 + 인프라 계측 + 코드베이스 조사 (2건 병렬 에이전트)

## 1. 테이블 이름 충돌 및 데이터 중복 (5건)

| # | 기획서 테이블 | 기존 테이블 | 문제 | 권고 |
|---|---|---|---|---|
| 1 | `go100_user_profile` | `go100_user_profiles` (22컬럼, 사용 중) | **이름 충돌** — 단수/복수 차이로 혼란 | 기존 테이블에 컬럼 추가(ALTER TABLE)로 통합 |
| 2 | `go100_minute_bars` | `v4_ohlcv_minute` (파티션 11GB, 1억+행) | **10GB 중복** — 동일 OHLCV 데이터 재저장 | VIEW 또는 기존 테이블 직접 사용, 신규 생성 금지 |
| 3 | `go100_investor_flow` | `v4_investor_daily` (171,301행) | **데이터 중복** — 투자자별 매매동향 이미 수집 중 | 기존 테이블 활용, 부족 컬럼만 추가 |
| 4 | `go100_tick_data` | `v4_tick_data` (존재, 0행) | 빈 테이블 재사용 가능 | 기존 테이블 스키마 수정 후 재사용 |

**결론**: 21개 신규 테이블 중 최소 5개는 기존 테이블과 충돌/중복. 디스크 11GB 남은 상태에서 10GB+ 중복 저장은 **서비스 중단 위험**.

## 3. KIS WebSocket 클라이언트 미구현

기획서는 "Phase 2에서 실시간 WebSocket 수집 구축"을 전제하지만:

- **현재 구현된 것**: FastAPI → 프론트엔드 브로드캐스트용 WebSocket 엔드포인트만 존재
- **미구현**: KIS 증권사 서버에 접속하는 **수신 클라이언트** (핵심)
- **WebSocket API 레지스트리**: 29개 API 정의는 되어 있으나, 실제 접속/구독/파싱 로직 없음
- **구독 제한**: 세션당 ~41종목 → 200종목 실시간 수집 시 **5개 세션 병렬 관리** 필요
- **예상 개발량**: 600~800줄, 2~3일 소요

**권고**: Phase 1에서는 REST 폴링(현행 유지)으로 충분. WebSocket은 Phase 2 후반에 별도 태스크로 분리.

## 4. 디스크 위기 — 잔여 11GB

| 항목 | 증가량 |
|---|---|
| v4_ohlcv_minute 파티션 (기존) | ~500MB/월 |
| 호가 데이터 (기획서대로) | 8.5GB/월 |
| 틱 데이터 | 2~5GB/월 |
| 기타 신규 테이블 | 1GB/월 |
| **합계** | **12~15GB/월** |

→ 기획서 Phase 1~2 데이터 수집을 모두 가동하면 **1개월 이내 디스크 풀**.

**권고**:
1. 디스크 증설(최소 100GB 추가) 또는 오래된 분봉 파티션 아카이브
2. 호가/틱은 일간 집계(1분봉 요약)로 전환
3. `go100_minute_bars` 신규 생성 금지 → `v4_ohlcv_minute` 직접 사용

## 6. 기존 cron 작업과의 충돌 주의

현재 crontab에 **14건 이상** 장후 수집 작업이 16:00~19:30에 집중. 기획서 Phase 1의 신규 수집 스크립트 추가 시 시간대 분산 필요.

## 결론

기획서 R2는 데이터 퍼스트 전략이 잘 정리되어 있으나, **디스크 용량 위기**(잔여 11GB)와 **테이블 중복**(10GB+ 낭비) 문제가 해결되지 않으면 Phase 1 착수 자체가 불가능. 위 6개 항목을 기획서에 반영 후 실행 권고.
