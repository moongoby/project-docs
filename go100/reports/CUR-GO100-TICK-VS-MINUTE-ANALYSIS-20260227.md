- **레포**: kis-autotrade-v4 (branch: phase-2c-command-center)

## 대표님 질문

> "실시간 수집에 분봉 진행하고 있지, 이걸 틱으로 대체해도 괜찮나? 틱으로 1분봉, 3분봉 등 필요한 걸 만들어 정리하면?"

---

## 1. 현재 아키텍처 (실시간 + 과거)

### A. 실시간 — WebSocket 틱 수집 (go100-ws-krx/nxt)

```
KIS WebSocket (H0STCNT0) ──→ 틱 원본 ──→ v4_tick_data (7일 보관)
       │
       └─→ _update_minute_bar() ──→ 1분봉 집계 ──→ v4_ohlcv_minute
```

| 항목 | 현재 설정 |
|------|----------|
| 수집 종목 | **30종목** (ws_stock_list.json) |
| WS 세션 제한 | 40종목/세션 |
| 수집 데이터 | 틱(체결) + 호가(10단계) |
| 1분봉 생성 | **이미 틱→1분봉 자동 집계 중** (kis_ws_collector.py:173) |
| 틱 보관 | 7일 후 자동 삭제 |
| 서비스 | go100-ws-krx (09:00~15:30), go100-ws-nxt (18:00~02:00) |

### B. 과거 배치 — REST API 분봉 수집 (collect_minute_historical.py)

```
KIS REST API (FHKST03010230) ──→ 1분봉 OHLCV ──→ v4_ohlcv_minute
```

| 항목 | 현재 설정 |
|------|----------|
| 수집 종목 | **3,841종목** (전종목 확대 중) |
| 수집 기간 | 1년 (244거래일) |
| API 속도 | 12 req/s |
| 데이터 양 | 4,370만건, ~10.2GB |
| 실행 시점 | 장후 16:00 cron |

### 핵심 발견

**실시간 수집은 이미 틱→1분봉 집계를 하고 있습니다.** `kis_ws_collector.py`의 `_update_minute_bar()` 함수가 틱마다 1분봉 OHLCV를 갱신하고 5초 간격으로 DB에 flush합니다.

## 3. "틱으로 대체" 시나리오 분석

### 시나리오 A: 실시간 틱 수집을 전종목으로 확대

#### 필요 자원

| 항목 | 계산 | 결과 |
|------|------|------|
| WS 세션 수 | 3,841종목 ÷ 40종목/세션 | **97세션** |
| KIS 계정 | 실계좌 1개(#7) + 모의 3개(#1,2,3) | 4계정 |
| 계정당 세션 | 97 ÷ 4 | ~25세션/계정 |

#### 불가능 사유

| # | 문제 | 상세 |
|---|------|------|
| 1 | **WS 동시 연결 제한** | KIS API는 계정당 WebSocket 동시 연결 수를 제한 (공식 문서상 1~5세션). 97세션은 불가능 |
| 2 | **서버 리소스** | 3,841종목 × 41,848틱/일 = **1.6억 틱/일**. DB INSERT 부하 극심 |
| 3 | **스토리지 폭발** | 1.6억건 × 150bytes = **24GB/일**. 1년이면 **5.8TB** |
| 4 | **모의계좌 틱 품질** | 모의계좌(#1,2,3) WS 틱 데이터는 실거래 체결이 아님 → 분봉 정확도 저하 |
| 5 | **소형주 틱 부재** | 거래대금 하위 종목은 체결 자체가 드물어 1분봉 빈칸 다수 |

**결론: 전종목 실시간 틱 수집은 현실적으로 불가능**

---

### 시나리오 B: 과거 분봉 수집(REST)을 틱으로 대체

#### 불가능 사유

| # | 문제 | 상세 |
|---|------|------|
| 1 | **과거 틱 API 없음** | KIS REST API에는 **과거 틱 데이터 조회 API가 존재하지 않음**. H0STCNT0은 실시간 전용. FHKST01010300(체결)은 당일 최근 30건만 |
| 2 | **Kiwoom ka10079** | 틱 차트 API가 있으나 1회 200건, 상위 20종목 한정. 3,841종목 × 244일 히스토리 불가 |
| 3 | **데이터 소급 불가** | 틱은 실시간으로 잡아야만 존재. 2025년 2월~2026년 2월 과거 틱은 어디에도 없음 |

**결론: 과거 분봉을 틱으로 대체하는 것은 원천적으로 불가능 (API 미존재)**

---

### 시나리오 C: 현재 구조 유지 + N분봉 파생 (권장)

```

                      │
                      ├─→ 3분봉 = CandleResampler.resample(1분봉, 3)
                      ├─→ 5분봉 = CandleResampler.resample(1분봉, 5)
```

## 4. 권장안

### 현재 구조가 최적인 이유

| 관점 | 현재 (REST 분봉 + WS 틱) | 틱 전면 전환 |
|------|--------------------------|-------------|
| **과거 데이터** | 1년 히스토리 확보 | 불가능 (API 없음) |
| **전종목 커버** | 3,841종목 가능 | 97세션 필요 (불가) |
| **스토리지** | ~25GB (1년 전종목) | ~5.8TB/년 (전종목 틱) |
| **N분봉 파생** | CandleResampler로 즉시 | 동일 |
| **실시간 정밀도** | 30종목 틱 + 분봉 집계 | 전종목은 불가 |
| **안정성** | REST=무상태, WS=30종목 | 97세션 관리 복잡 |

### 개선 가능 사항

| # | 개선안 | 효과 | 난이도 |
|---|--------|------|--------|
| 1 | **실시간 WS 종목 확대**: 30→80종목 (2세션) | 주요 종목 틱+호가 커버 확대 | 낮음 |
| 2 | **N분봉 API 추가**: `/api/go100/chart/resample?stock=005930&minutes=3` | 백억이 채팅에서 3분봉/5분봉 조회 | 중간 |
| 3 | **틱 보관 확대**: 7일→30일 (주요 30종목) | 단기 틱 분석 가능 | 낮음 |
| 4 | **틱→분봉 백필**: 장후 REST 배치에서 WS 미수집 종목 보충 | 현재 구조 (이미 동작 중) | 없음 |

## 5. 종합 결론

```
Q: 틱으로 분봉을 대체해도 괜찮나?
A: 아니요. 현재 구조가 최적입니다.

이유 3가지:
1. 과거 틱 데이터 API가 없음 → 히스토리 분봉은 REST로만 가능
2. 전종목 실시간 틱은 WS 세션 제한(40종목/세션)으로 불가
3. 1분봉만 있으면 N분봉 파생은 이미 구현된 CandleResampler로 즉시 가능

현재 최적 구조:
┌─────────────────────────────────┐
│ 과거: REST 1분봉 (전종목×1년)    │ ← 대체 불가
│ 실시간: WS 틱→1분봉 (30종목)     │ ← 이미 틱 기반
│ 파생: 1분봉→3/5/10/30/60분봉    │ ← 이미 구현됨
└─────────────────────────────────┘
```

### 실시간 틱 수집은 이미 하고 있습니다

`go100-ws-krx` 서비스가 30개 핵심 종목에 대해 실시간 틱을 수집하고, 이를 자동으로 1분봉(`v4_ohlcv_minute`)으로 집계하고 있습니다. 오늘 87만 8천건의 틱이 수집되어 7,305개의 1분봉으로 정확히 변환되었습니다.

과거 분봉 배치(REST)는 WS로 커버하지 못하는 **3,811종목의 히스토리 보충** 역할이므로, 두 방식이 상호 보완적으로 동작하는 현재 구조가 가장 효율적입니다.
