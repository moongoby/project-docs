# 디스크 긴급 정리 (1·2단계 실행)

**작성일시:** 2026-02-23
**작업 유형:** 설정 변경 / 점검
**상태:** 완료 (1·2단계), 3단계는 확인 후 판단
**관련 파일:** 없음 (시스템/로그/Docker 정리)

---

## 1. 작업 개요

디스크 100%로 인한 서비스 중단 방지를 위해 1단계 현황 파악 → 2단계 안전 정리까지 실행하고, 3단계(프로젝트 데이터)는 후보만 확인한 상태입니다.

---

## 3. 2단계 실행 결과 (즉시 정리)

- `journalctl --vacuum-size=100M` → 저널 약 2.4G → 100M 수준으로 축소
- `truncate` 로그 → newtalk_cron.log, newtalk_backup.log, *.log, syslog 비움
- `apt-get clean` 실행
- **Docker system prune -af** → **약 4.48GB 회수**
- `/tmp/*` 정리

### 정리 후 디스크
- **사용량:** 645G → **639G**
- **여유:** 186G → **192G**
- **사용률:** 78% → **77%**

### 로그 재확인
- /var/log/journal: **17M**
- newtalk_cron.log / newtalk_backup.log: **0**
- btmp: 132M (유지)

---

## 4. 3단계 후보 (확인만, 삭제는 미실행)

- **/data/styleflow/raw:** 5.5G (원본 MOV 등). chicblack/20260220만 약 147M.
- **/data** 내 10MB 이상 `.log` 파일: 없음.
- **.bak/.old/.tmp:** `/data/shortflow/worker/workers/pipeline_worker.py.bak` 1건.

추가 확보가 필요하면 raw 오래된 날짜/브랜드별 정리 또는 btmp 로테이션 검토.

---

## 5. 주의사항 / 후속 작업

- newtalk_cron.log, newtalk_backup.log는 계속 쌓이므로 **로테이션(logrotate)** 설정 권장.
- 디스크가 다시 올라가면 `/data/styleflow/raw` 오래된 폴더 정리 또는 NAS 이관 검토.
- btmp(실패 로그인) 132M는 필요 시 `sudo truncate -s 0 /var/log/btmp` 로 비울 수 있음(보안 감사 필요 시 보존).
