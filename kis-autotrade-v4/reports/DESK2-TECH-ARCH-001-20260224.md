## Part 1. 시스템 개요

### 1.1 목적

이 문서는 KIS-AUTOTRADE V4.1 시스템의 DESK 2 모듈에 대한 전체 기술 명세와 소프트웨어 아키텍처를 정의합니다. DESK 2는 "데일리 타임프레임(장중 5분~장 마감)"에서 고확률 종목을 발굴하고, 7개 독립 전략 엔진에 전달하여 최적 타이밍에 진입·청산하는 복합 수익 추출 시스템입니다. 하루 2~5건의 독립 거래를 실행하며, 건당 +3~10% 수익을 목표로 합니다. 릴레이 매칭을 통해 동일 종목에서 복수 수익 기회를 포착하고, 자본 규모별 5단계 TIER 시스템으로 리스크를 제어합니다.

### 1.2 설계 원칙

**원칙 1 — 발굴과 실행의 완전 분리.** DESK 2는 종목을 찾는 일만 합니다. 전략은 타이밍을 결정하는 일만 합니다. 어떤 전략도 독자적으로 종목을 탐색하지 않으며, DESK 2가 전달하지 않은 종목에는 어떤 전략도 진입하지 않습니다.

**원칙 2 — 시간 비의존적 연속 스캐닝.** 7개 발굴 조건은 특정 시간대에 고정되지 않습니다. 08:50부터 15:00까지 전 구간에서 실시간으로 시장을 감시하며, 조건이 충족되는 즉시 전략에 종목을 전달합니다.

**원칙 3 — 단일 종목 단일 전략.** 동일 시점에 하나의 종목에는 하나의 전략만 진입합니다. 복합 점수가 가장 높은 전략이 우선권을 갖습니다.

**원칙 4 — 상태 전환과 릴레이.** 종목의 시장 상태가 변하면 DESK 2가 상태 전환을 감지하고, 새로운 조건의 주력 전략으로 릴레이합니다. 하루 동일 종목 최대 3회 릴레이까지 허용됩니다.

**원칙 5 — 자본 규모 적응.** 시스템은 자본 크기에 따라 활성 엔진 수, 포지션 한도, 건당 배분 비율, 목표 시가총액 범위를 자동 조절합니다.

### 1.3 시스템 경계

DESK 2 모듈은 KIS-AUTOTRADE V4.1 전체 아키텍처 내에서 다음 외부 시스템과 인터페이스합니다. 상위 시스템으로는 Orchestrator(전체 DESK 1~4 조율, 레짐 판단, 전체 자본 배분)가 있고, 데이터 소스로는 KIS OpenAPI(실시간 시세, 호가, 체결), 분봉 수집기(1분/3분/5분 OHLCV), 뉴스 피드(실시간 공시·뉴스), 섹터 데이터(v4_sector_price)가 있으며, 실행 시스템으로는 KIS 주문 API(매수·매도·정정·취소)가 있고, 저장소로는 PostgreSQL(거래 로그, 백테스트 결과), Redis(실시간 상태, 대기열, 점수 캐시)가 있습니다.

## Part 2. 아키텍처

### 2.1 계층 구조

전체 DESK 2 시스템은 5개 계층으로 구성됩니다.

**Layer 0 — Data Ingestion Layer (데이터 수집 계층).** 시장 데이터를 수집하고 정규화하여 상위 계층에 공급합니다. 이 계층은 WebSocket을 통해 KIS OpenAPI로부터 실시간 체결·호가 데이터를 수신하고, 1분/3분/5분 봉을 실시간으로 생성하며, 뉴스·공시 피드를 수신하여 종목 코드에 태깅하고, VWAP·RVOL·RSI·볼린저밴드 등 기술 지표를 실시간으로 계산합니다. 이 계층의 출력은 TickStream(종목별 실시간 체결 스트림), BarStream(종목별 분봉 스트림), IndicatorCache(종목별 지표 실시간 캐시), NewsStream(종목 태깅된 뉴스 이벤트)입니다.

**Layer 1 — Discovery Layer (DESK 2 발굴 계층).** 7개 발굴 조건(Condition)이 독립적으로 실행되며, 각 조건은 Layer 0의 데이터를 소비하여 조건 충족 종목을 발굴하고, DESK 점수(0~100)를 산출합니다. 각 Condition은 독립 프로세스로 실행되며, 서로 간 의존성이 없습니다. 조건 충족 시 DiscoverySignal 객체를 생성하여 Layer 2로 전달합니다.

DiscoverySignal의 데이터 구조는 다음과 같습니다. ticker(종목 코드), condition_id(1~7 중 발굴 조건 번호), desk_score(0~100 정수, DESK 점수), timestamp(발굴 시각), market_state(종목의 현재 시장 상태 분류), metadata(조건별 부가 데이터로, 갭률·RVOL·VI 발동 횟수 등 포함), primary_strategy(주력 매칭 전략 ID), cross_strategies(크로스 매칭 가능 전략 ID와 적합도 점수 리스트)입니다.

**Layer 2 — Strategy Layer (전략 실행 계층).** 7개 전략 엔진이 독립적으로 실행됩니다. 각 전략은 Layer 1로부터 DiscoverySignal을 수신하고, 해당 종목의 실시간 데이터를 분석하여 진입 타이밍을 결정하며, CS(Confidence Score, 0~100)를 산출합니다. CS가 50 이상이면 TradeSignal을 생성하여 Layer 3으로 전달하고, 50 미만이면 대기 상태로 CS를 지속 갱신합니다.

TradeSignal의 데이터 구조는 다음과 같습니다. ticker(종목 코드), strategy_id(전략 ID), cs(0~100 정수, Confidence Score), entry_price(권장 진입가), stop_loss(손절가), target_prices(목표가 리스트로, 분할 청산용), position_size_pct(권장 포지션 비율), max_hold_time(최대 보유 시간, 초 단위), timestamp(신호 생성 시각), discovery_signal_ref(원본 DiscoverySignal 참조)입니다.

**Layer 3 — Orchestration Layer (조합·의사결정 계층).** 이 계층이 DESK 2의 두뇌입니다. Layer 1과 Layer 2의 신호를 종합하여 최종 매매 의사결정을 내립니다. 핵심 기능은 다섯 가지입니다. 첫째, 복합 점수 산출(DESK 점수 × CS ÷ 100). 둘째, 종목 간 우선순위 결정(복합 점수 내림차순). 셋째, 충돌 해결(동일 종목 다중 전략, 동일 업종 중복). 넷째, 자본 배분(TIER 엔진 연동). 다섯째, 릴레이 관리(상태 전환 감지, 전략 교체, 횟수 제한).

**Layer 4 — Execution Layer (실행 계층).** Layer 3의 최종 결정을 실제 주문으로 변환합니다. 주문 분할(TIER 4~5에서 대량 주문 시 3~5회 분할), 슬리피지 모니터링, 체결 확인, 포지션 추적, 청산 실행(목표가·손절가·시간 초과·트레일링 스탑)을 수행합니다.

### 2.3 컴포넌트 상세 명세

#### 2.3.1 Layer 0 — Data Ingestion

**TickCollector.** KIS OpenAPI WebSocket으로부터 실시간 체결 데이터를 수신합니다. 종목당 초당 최대 100건의 체결을 처리하며, 각 체결을 TickEvent(ticker, price, volume, timestamp, side)로 정규화합니다. Redis Pub/Sub 채널 `tick:{ticker}`로 발행합니다.

**BarBuilder.** TickEvent를 소비하여 1분/3분/5분 OHLCV 봉을 실시간으로 생성합니다. 봉 완성 시 BarEvent(ticker, timeframe, open, high, low, close, volume, timestamp)를 Redis Pub/Sub 채널 `bar:{ticker}:{timeframe}`으로 발행합니다. 미완성 봉도 partial_bar로 500ms 간격 갱신합니다.

**IndicatorEngine.** BarEvent를 소비하여 기술 지표를 실시간 계산합니다. 계산 대상 지표는 VWAP(장중 누적), RVOL(현재 거래량 ÷ 20일 동시간 평균 거래량), RSI(14봉 기준), 볼린저밴드(20봉, 2σ), ATR(14봉), MA5/MA10/MA20, 체결강도(매수체결량 ÷ 매도체결량 × 100)입니다. 결과는 Redis Hash `indicator:{ticker}`에 저장되며, 봉 완성 시마다 갱신됩니다.

**NewsCollector.** 실시간 공시·뉴스 피드를 수신하여 종목 코드를 태깅합니다. NewsEvent(ticker, headline, source, category, timestamp)를 Redis Pub/Sub 채널 `news:{ticker}`로 발행합니다. 카테고리는 실적, 수주, M&A, 규제, 테마, 기타로 분류됩니다.

**OrderBookCollector.** 호가 데이터를 수신하여 매수·매도 10호가의 잔량, 스프레드, 매수·매도 비율을 계산합니다. OrderBookSnapshot(ticker, bid_prices, bid_volumes, ask_prices, ask_volumes, spread, buy_ratio, timestamp)을 Redis Hash `orderbook:{ticker}`에 500ms 간격 갱신합니다.

#### 2.3.2 Layer 1 — Discovery Conditions

**공통 인터페이스.** 모든 Condition은 `BaseCondition` 추상 클래스를 상속하며, 다음 메서드를 구현합니다.

`scan()` — 전체 유니버스를 스캔하여 조건 충족 종목 리스트를 반환합니다. 500ms 간격으로 호출됩니다.

`score(ticker)` — 특정 종목의 DESK 점수(0~100)를 계산합니다.

`emit(ticker, score)` — DiscoverySignal을 생성하여 Redis 채널 `discovery:{condition_id}`로 발행합니다.

각 Condition의 상세 명세는 다음과 같습니다.

**Condition 1 — GapDiscovery (갭 발화).** 스캔 주기 500ms, 활성 시간 08:50~15:00. 발굴 기준은 시가 갭 ≥ +3% AND ≤ +8%(당일 시가 ÷ 전일 종가 − 1), RVOL ≥ 3.0(장 시작 후에는 현재 시점 기준 동시간 비교), 시가총액 ≥ 500억, 뉴스·공시 존재(NewsEvent 30분 이내)입니다. 점수 산정은 갭 크기(+3%=0점, +5%=15점, +8%=25점, 선형 보간) 25점, RVOL(3.0=0점, 5.0=10점, 10.0+=20점) 20점, 뉴스 강도(테마=5점, 수주=10점, 실적=15점, M&A=20점) 20점, 체결 강도(100%=0점, 130%=10점, 150%+=20점) 20점, 호가 스프레드(0.5%=0점, 0.3%=10점, 0.15%이하=15점) 15점입니다. 합산 100점이며, 60점 미만은 폐기됩니다. 주력 전략 ALPHA-GAP, 크로스 매칭 가능 전략은 BRAVO-ORB(적합도 60), CHARLIE-VI(55), ECHO-ABCD(65)입니다.

**Condition 2 — RangeBreakoutDiscovery (레인지 돌파).** 스캔 주기 500ms, 활성 시간 08:50~15:00. 발굴 기준은 특정 N분 구간(기본값 15분, 09:05 기준이 아닌 임의 시점) 내 고가-저가 레인지 폭이 현재가의 1.5~4%, RVOL ≥ 2.0, 레인지 내 상방 체결 비중 > 60%, 당일 거래대금 상위 100위 이내입니다. 점수 산정은 돌파 강도(고가 대비 초과율 0.3%=10점, 0.5%=15점, 1%+=20점) 20점, 거래량 동반(돌파 봉 거래량 ÷ 레인지 평균 거래량, 1.5×=10점, 2×=15점, 3×+=20점) 20점, 레인지 형성 시간(5분=5점, 10분=10점, 15분+=20점, 길수록 신뢰도 높음) 20점, RVOL(2.0=5점, 3.0=10점, 5.0+=20점) 20점, 시장 방향(KOSPI/KOSDAQ 지수 양봉=10점, 음봉=0점, 강한 양봉=20점) 20점입니다. 60점 미만 폐기. 주력 전략 BRAVO-ORB, 크로스 매칭 DELTA-VWAP(55), ECHO-ABCD(50)입니다.

**Condition 3 — VIExplosionDiscovery (VI 폭발).** 스캔 주기 이벤트 기반(VI 발동 이벤트 수신 시 즉시), 활성 시간 09:00~14:30. 발굴 기준은 동적 VI 발동(상한), 발동 전 5분 RVOL ≥ 5.0, 당일 해당 종목 VI 발동 횟수 ≤ 2회(3회 이상은 과열 판단), 시가총액 ≥ 300억입니다. 점수 산정은 RVOL(5.0=10점, 10.0=15점, 20.0+=25점) 25점, VI 직전 상승률(3%=5점, 5%=10점, 8%+=20점) 20점, 호가 매수 잔량 비율(50%=0점, 60%=10점, 70%+=20점) 20점, 뉴스·공시 존재(없음=0점, 있음=20점) 20점, VI 발동 횟수(1회차=15점, 2회차=5점) 15점입니다. 60점 미만 폐기. 주력 전략 CHARLIE-VI, 크로스 매칭 ALPHA-GAP(70), ECHO-ABCD(55), GOLF-REVERSAL(50)입니다.

#### 2.3.3 Layer 2 — Strategy Engines

**공통 인터페이스.** 모든 Strategy는 `BaseStrategy` 추상 클래스를 상속하며, 다음 메서드를 구현합니다.

`evaluate(discovery_signal)` — DiscoverySignal을 받아 해당 종목의 진입 조건을 평가하고 CS를 산출합니다.

`generate_signal()` — CS ≥ 50이면 TradeSignal을 생성합니다.

`update()` — 매 500ms 호출되어 CS를 실시간 갱신합니다(대기 중인 종목에 대해).

`manage_position(position)` — 진입 후 포지션 관리(트레일링, 분할 청산, 시간 초과 등).

각 전략의 상세 명세는 다음과 같습니다.

**ALPHA-GAP (갭 포착).** 진입 조건은 3분봉 연속 2개 양봉이고, 두 번째 양봉 종가 > VWAP이며, 체결 강도 ≥ 120%입니다. #### 2.3.4 Layer 3 — Orchestration

**CompositeScoreCalculator.** 모든 활성 TradeSignal에 대해 복합 점수 = DESK Score × CS ÷ 100을 계산합니다. 동일 종목에 대해 복수 전략이 신호를 낸 경우, 최고 복합 점수 전략만 유지하고 나머지는 대기열로 이동합니다.

**PriorityRanker.** 복합 점수 내림차순으로 전체 TradeSignal을 정렬합니다. 동일 업종 종목이 이미 진입 중이면 해당 업종 종목은 순위에서 제외합니다. 복합 점수 40점 미만은 폐기합니다.

**CapitalAllocator.** TIER 엔진과 연동하여 현재 자본 규모에 따른 건당 배분 비율, 최대 동시 포지션 수, 일일 손실 한도를 적용합니다. TIER 1(~₩10M)은 건당 90~100%, 최대 1포지션, 일일 손실 -3%입니다. TIER 2(~₩50M)는 건당 60%, 최대 2포지션, 일일 손실 -4%입니다. TIER 3(~₩100M)은 건당 40%, 최대 3포지션, 일일 손실 -4%입니다. TIER 4(~₩1B)는 건당 30%, 최대 4포지션, 일일 손실 -3%입니다. TIER 5(₩1B+)는 건당 15%, 최대 6~8포지션, 일일 손실 -2%입니다. 복리 적용 방식: 수익 실현 시 가용 자본이 즉시 갱신되며, 다음 진입의 배분 비율은 갱신된 자본 기준으로 적용됩니다.

**RelayManager.** 포지션이 청산된 종목에 대해, 해당 종목의 현재 시장 상태를 재평가합니다. Layer 1의 7개 Condition이 재스캔하여 새로운 DiscoverySignal이 발생하면, 이전 전략과 다른 전략으로 릴레이 진입합니다. 릴레이 규칙은 다음과 같습니다. 동일 종목 일일 릴레이 최대 3회, 릴레이 간 최소 대기 시간 5분(냉각), 릴레이 진입의 복합 점수는 기존 진입보다 높아야 합니다(점진적 악화 방지).

**ConflictResolver.** 충돌 해결 규칙은 세 가지입니다. 첫째, 동일 종목 충돌: 복합 점수 최고 전략만 진입, 나머지 대기. 둘째, 동일 업종 충돌: 이미 진입 종목과 같은 업종 진입 금지. 셋째, 자본 충돌: 가용 자본 부족 시 대기열 1순위로 이동, 기존 포지션 청산 후 자동 진입.

**WaitQueue.** 진입하지 못한 TradeSignal을 대기열에 보관합니다. 500ms 간격으로 CS를 재계산하며, 기존 포지션 청산 시 대기열 1순위(복합 점수 최고)가 자동 진입합니다. CS가 50 미만으로 하락하면 대기열에서 제거됩니다.

#### 2.3.5 Layer 4 — Execution

**OrderManager.** Layer 3의 ExecutionOrder를 받아 KIS 주문 API로 실제 주문을 전송합니다. TIER 4~5에서 주문 금액 ≥ ₩50M일 경우 3~5회로 분할하며, 분할 간격은 10초, 각 분할은 시장가 또는 최유리 지정가입니다.

**PositionTracker.** 모든 활성 포지션의 실시간 상태를 추적합니다. 포지션별 데이터는 ticker, strategy_id, entry_price, current_price, unrealized_pnl, hold_time, stop_loss, target_prices, trail_stop입니다. 500ms 간격으로 갱신됩니다.

**ExitManager.** 각 전략의 청산 규칙을 실행합니다. 목표가 도달(분할 청산), 손절가 도달(전량 즉시 청산), 시간 초과(전량 청산), 트레일링 스탑(직전 봉 저가 기준 동적 조정) 네 가지 청산 유형을 처리합니다. 청산 시 RelayManager에 종목 상태 재평가를 요청합니다.

**SlippageMonitor.** 체결가와 신호가의 차이(슬리피지)를 실시간 추적합니다. 전략별 평균 슬리피지를 누적 계산하며, 슬리피지가 0.5%를 초과하면 해당 전략의 CS에 -10점 페널티를 적용합니다.

**TradeLogger.** 모든 거래를 PostgreSQL에 기록합니다. 기록 항목은 ticker, strategy_id, condition_id, entry_time, exit_time, entry_price, exit_price, pnl_pct, pnl_amount, hold_seconds, desk_score, cs, composite_score, relay_count, tier, slippage입니다.

## Part 3. 상태 관리 및 생명주기

### 3.1 종목 상태 머신

DESK 2 시스템 내에서 각 종목은 다음 상태를 순환합니다.

**IDLE** → 스캔 대상이지만 아직 어떤 조건도 충족하지 않은 상태입니다.

**DISCOVERED** → Condition 중 하나가 해당 종목을 발굴하여 DiscoverySignal이 발행된 상태입니다. DESK 점수 ≥ 60입니다.

**EVALUATING** → 매칭된 전략이 CS를 계산 중인 상태입니다. CS < 50이면 WAITING으로 전환, CS ≥ 50이면 READY로 전환됩니다.

**WAITING** → CS가 아직 50 미만이어서 대기 중인 상태입니다. 500ms 간격 CS 재계산, CS ≥ 50이 되면 READY로 전환, DESK 점수가 60 미만으로 하락하면 IDLE로 복귀합니다.

**READY** → CS ≥ 50이고 Orchestrator의 자본 배분을 기다리는 상태입니다. 복합 점수 순위에 따라 ACTIVE 또는 QUEUED로 전환됩니다.

**QUEUED** → 자본 부족 또는 업종 충돌로 대기열에 있는 상태입니다. 포지션 청산 시 자동 전환 가능합니다.

**ACTIVE** → 실제 포지션이 진입된 상태입니다. ExitManager가 청산 조건을 모니터링합니다.

**EXITED** → 포지션이 청산된 상태입니다. RelayManager가 상태 재평가를 수행합니다.

**RELAY_EVALUATING** → 청산 후 새로운 Condition에 의해 재발굴되어 다른 전략으로 릴레이 진입을 평가 중인 상태입니다. 릴레이 횟수 < 3이면 EVALUATING과 동일 흐름, ≥ 3이면 COOLDOWN으로 전환됩니다.

**COOLDOWN** → 릴레이 3회 소진 또는 연속 손절로 인한 냉각 상태입니다. 해당 종목은 당일 추가 진입 불가합니다.

상태 전이도는 다음과 같습니다.

```
IDLE ──[Condition 충족]──→ DISCOVERED ──→ EVALUATING
                                              │
                              ┌─[CS<50]──→ WAITING ──[CS≥50]─┐
                              │                               │
                              └─[CS≥50]──→ READY ←────────────┘
                                            │
                             ┌─[자본OK]──→ ACTIVE
                             │              │
                             └─[대기]──→ QUEUED ──[자본확보]──→ ACTIVE
                                                                │
                                            ┌───[청산]──→ EXITED
                                            │               │
                                            │    ┌─[릴레이<3]──→ RELAY_EVALUATING ──→ EVALUATING
                                            │    │
                                            │    └─[릴레이≥3]──→ COOLDOWN ──→ IDLE(익일)
                                            │
                                            └───[손절3연속]──→ COOLDOWN
```

### 3.2 전략 엔진 상태 머신

각 전략 엔진은 다음 상태를 가집니다.

**STANDBY** → DiscoverySignal 대기 중. 매칭되는 조건의 신호가 오면 SCANNING으로 전환됩니다.

**SCANNING** → 전달받은 종목의 실시간 데이터를 분석하여 CS를 계산 중입니다. CS ≥ 50이면 SIGNAL_READY, CS < 50이면 MONITORING으로 전환됩니다.

**MONITORING** → CS가 아직 기준 미달이지만 종목이 여전히 DISCOVERED/WAITING 상태이므로 계속 관찰합니다. 500ms 갱신합니다.

**SIGNAL_READY** → TradeSignal을 Orchestrator에 전달한 상태입니다. Orchestrator 승인 시 EXECUTING, 거부 시 MONITORING으로 복귀됩니다.

**EXECUTING** → 실제 포지션 관리 중입니다. manage_position()이 활성화되어 청산 조건을 모니터링합니다.

**COMPLETED** → 포지션 청산 완료입니다. RelayManager 알림 후 STANDBY로 복귀됩니다.

## Part 4. 통신 프로토콜 및 데이터 모델

### 4.1 내부 통신 아키텍처

모든 계층 간 통신은 Redis Pub/Sub과 Redis Stream을 사용합니다. Pub/Sub은 실시간 이벤트(TickEvent, BarEvent, NewsEvent)에 사용되며, 지연 < 1ms가 요구됩니다. Redis Stream은 DiscoverySignal, TradeSignal, ExecutionOrder 등 순서 보장이 필요한 신호에 사용되며, Consumer Group을 통해 신호 유실을 방지합니다.

채널 설계는 다음과 같습니다. `tick:{ticker}` — 종목별 실시간 체결, `bar:{ticker}:{timeframe}` — 종목별 분봉(1m/3m/5m), `indicator:{ticker}` — Redis Hash, 종목별 지표 캐시, `news:{ticker}` — 종목별 뉴스 이벤트, `orderbook:{ticker}` — Redis Hash, 종목별 호가, `discovery:stream` — Redis Stream, DiscoverySignal, `trade:stream` — Redis Stream, TradeSignal, `execution:stream` — Redis Stream, ExecutionOrder, `position:{ticker}` — Redis Hash, 포지션 실시간 상태, `state:{ticker}` — Redis Hash, 종목 상태 머신 현재 상태입니다.

## Part 5. 적합도 매트릭스 및 릴레이 엔진 상세

### 5.1 정적 적합도 매트릭스

7개 Condition × 7개 Strategy의 기본 적합도 점수(0~100)는 사전 정의됩니다. 이 값은 백테스트 결과에 따라 분기별로 갱신됩니다.

```
              ALPHA  BRAVO  CHARLIE  DELTA  ECHO  FOXTROT  GOLF
C1 (GAP)       95     60      55      30     65      20     15
C2 (ORB)       40     95      35      55     50      20     15
C3 (VI)        70     30      95      40     55      25     50
C4 (VWAP)      20     45      25      90     60      30     55
C5 (ABCD)      35     40      30      55     95      40     30
C6 (SECTOR)    30     50      25      45     40      90     20
C7 (OVERSOLD)  15     20      40      55     30      15     90
```

주력 매칭은 대각선(C1-ALPHA, C2-BRAVO, ..., C7-GOLF)이며, 적합도 90~95입니다. 크로스 매칭은 적합도 50 이상인 비대각 셀이며, 이는 릴레이 또는 주력 전략 CS 부족 시 대체 전략으로 사용됩니다.

### 5.2 동적 적합도 조정

시장 레짐에 따라 정적 적합도에 보정값을 적용합니다.

**상승 레짐(KOSPI/KOSDAQ 5일 MA > 20일 MA, ADX ≥ 20):** 모멘텀 전략(ALPHA, BRAVO, CHARLIE) 적합도 +10, 평균회귀 전략(GOLF) 적합도 -10입니다.

**하락 레짐(KOSPI/KOSDAQ 5일 MA < 20일 MA, ADX ≥ 20):** 모멘텀 전략 적합도 -15, 평균회귀 전략 +15, FOXTROT-SECTOR -20(업종 동반 하락 가능성)입니다.

**횡보 레짐(ADX < 20):** 레인지 전략(BRAVO, DELTA) +10, 추세 전략(ECHO, FOXTROT) -10입니다.

**고변동 레짐(VKOSPI > 25):** CHARLIE-VI +15(VI 빈도 증가), 전체 전략 손절 폭 0.5%p 축소입니다.

### 5.3 릴레이 엔진 상세

릴레이 엔진은 RelayManager 컴포넌트가 담당하며, 다음 프로세스를 실행합니다.

**트리거.** ExitManager가 포지션을 청산하면, RelayManager에 RELAY_CHECK 이벤트를 발행합니다. 이벤트에는 ticker, exited_strategy_id, exit_reason(profit/stop/timeout), relay_count가 포함됩니다.

**평가.** relay_count < 3이면 진행합니다. relay_count ≥ 3이면 COOLDOWN으로 전환하고 중단합니다. 5분 냉각 타이머를 시작합니다. 냉각 완료 후, 해당 종목의 현재 시장 상태를 Layer 1의 7개 Condition에 재질의합니다. 새로운 DiscoverySignal이 발생하면, 이전 전략과 다른 전략의 CS를 평가합니다. 새로운 복합 점수가 이전 진입의 복합 점수 이상이면 릴레이를 승인합니다.

**실행.** 승인된 릴레이는 일반 진입과 동일하게 Orchestrator → Execution 경로를 따릅니다. TradeSignal의 is_relay = True, relay_count = 이전 값 + 1로 설정됩니다.

**제한.** 동일 종목 일일 릴레이 최대 3회, 릴레이 간 최소 냉각 5분, 릴레이 손절 시 해당 종목 즉시 COOLDOWN(추가 릴레이 금지), 14:00 이후 릴레이 금지(청산 시간 확보)입니다.

## Part 6. 자본 관리 엔진(TIER) 상세

### 6.1 TIER 판정 로직

매일 08:30 시스템 부팅 시, 전일 종가 기준 계좌 순자산을 확인하여 TIER를 판정합니다.

TIER 판정 기준은 다음과 같습니다. 순자산 < ₩10M이면 TIER 1, ₩10M 이상 ₩50M 미만이면 TIER 2, ₩50M 이상 ₩100M 미만이면 TIER 3, ₩100M 이상 ₩1B 미만이면 TIER 4, ₩1B 이상이면 TIER 5입니다.

상향 전환은 차상위 TIER 기준의 70%에 도달하면 주간 평가 시(금요일 15:30) 적용됩니다. 예를 들어 TIER 1에서 ₩7M 도달 시 TIER 2로 전환됩니다. 하향 전환은 현 TIER 하한선 미달 시 즉시 적용됩니다.

### 6.2 TIER별 파라미터 상세

**TIER 1 (₩1M~₩10M).** 활성 Condition은 C1(갭), C3(VI) 2개입니다. 활성 전략은 ALPHA-GAP, CHARLIE-VI 2개입니다. 건당 자본 배분 90~100%, 최대 동시 포지션 1개, 일일 목표 수익 +3~5%, 일일 손실 한도 -3%, 대상 시가총액 ₩100B~₩500B, 최소 CS 85점입니다. TIER 1은 자본이 작으므로 가장 기대값이 높은 2개 전략에 집중하여 빠른 자본 성장을 추구합니다.

**TIER 2 (₩10M~₩50M).** 활성 Condition은 C1, C2, C3, C5 4개입니다. 활성 전략은 ALPHA-GAP, BRAVO-ORB, CHARLIE-VI, ECHO-ABCD 4개입니다. 건당 자본 배분 60%, 최대 동시 포지션 2개, 일일 목표 +2~4%, 일일 손실 -4%, 대상 시가총액 ₩100B~₩1T, 최소 CS 75점입니다.

**TIER 3 (₩50M~₩100M).** 활성 Condition은 C1~C7 전부 7개입니다. 활성 전략도 7개 전부입니다. 건당 자본 배분 40%, 최대 동시 포지션 3개, 일일 목표 +1.5~3%, 일일 손실 -4%, 대상 시가총액 ₩300B 이상, 최소 CS 65점입니다.

**TIER 4 (₩100M~₩1B).** 활성 Condition 7개, 활성 전략 7개입니다. 건당 자본 배분 30%, 최대 동시 포지션 4개, 일일 목표 +1~2.5%, 일일 손실 -3%, 대상 시가총액 ₩500B 이상(KOSPI 30% 편입), 최소 CS 60점입니다. 주문 분할 적용: ₩50M 이상 주문은 3~5회 분할, 10초 간격입니다.

**TIER 5 (₩1B+).** 활성 Condition 7개 + 추가 조건(HOTEL-PAIR, INDIA-BASKET) 9개, 활성 전략 9개입니다. 건당 자본 배분 15%, 최대 동시 포지션 6~8개, 일일 목표 +0.8~1.5%, 일일 손실 -2%, 대상 시가총액 ₩1T 이상(KOSPI 50% 편입), 최소 CS 60점입니다. 안전금고 배분: 전체 자본의 20~40%를 비운용 현금으로 유지합니다. 주문 분할 강화: ₩30M 이상 주문은 5~7회 분할, 15초 간격입니다.

### 6.3 장중 복리 메커니즘

DESK 2의 복리는 일 단위가 아닌 거래 단위로 적용됩니다. 첫 번째 거래에서 수익이 발생하면, 가용 자본이 즉시 증가하고, 두 번째 거래의 건당 배분 금액은 증가된 자본 × TIER 배분 비율로 계산됩니다.

예시(TIER 2, 초기 자본 ₩30M): 1차 거래 배분 ₩18M(60%), 수익 +5% = ₩0.9M 실현, 가용 자본 ₩30.9M. 2차 거래 배분 ₩18.54M(₩30.9M × 60%), 수익 +4% = ₩0.74M 실현, 가용 자본 ₩31.64M. 3차 거래 배분 ₩18.98M(₩31.64M × 60%). 하루 3건으로 ₩30M → ₩31.64M, 일일 +5.47%(단순 합산 +9%가 아닌 복리 기반 실제 자본 증가)입니다.

## Part 7. 리스크 관리 체계

### 7.1 계층별 리스크 한도

**거래 단위.** 건당 최대 손실 = TIER별 일일 손실 한도 ÷ 최대 포지션 수입니다. TIER 1: -3% ÷ 1 = -3%, TIER 2: -4% ÷ 2 = -2%, TIER 3: -4% ÷ 3 = -1.33%, TIER 4: -3% ÷ 4 = -0.75%, TIER 5: -2% ÷ 8 = -0.25%입니다.

**전략 단위.** 각 전략의 일일 누적 손실이 -2%를 초과하면 해당 전략을 당일 비활성화합니다. 연속 3회 손절 시 1시간 냉각 후 CS 기준을 +10점 상향합니다.

**DESK 2 전체.** 일일 손실 한도 도달 시 DESK 2 전체를 비활성화하고 전 포지션을 청산합니다. 주간 손실이 -8%를 초과하면 다음 주 TIER를 1단계 하향합니다.

### 7.2 Hard Kill 규칙

관리종목·투자위험종목 진입 금지, 당일 ±15% 변동 종목 진입 금지(VI 전략 예외 시 상한만 +15%까지 허용), 실적 발표 전후 2 거래일 진입 금지, 시가총액 TIER별 하한선 미달 종목 진입 금지, 14:30 이후 신규 진입 금지, 동일 업종 2종목 이상 동시 보유 금지입니다.

### 7.3 Soft Kill 규칙

VKOSPI > 25 시 전체 포지션 50% 축소, 동일 업종 비중 30% 초과 시 추가 진입 금지(이미 Hard Kill에 의해 차단되지만 비중 기준으로 이중 검증), 전략 연속 3회 손절 시 1시간 냉각, KOSPI/KOSDAQ 지수 당일 -2% 이상 하락 시 모멘텀 전략(ALPHA, BRAVO, CHARLIE) 오전 11시까지 진입 유예입니다.

### 7.4 비상 프로토콜

**Circuit Breaker Level 1 (일일 손실 -3% 도달).** 신규 진입 중단, 기존 포지션 트레일링 스탑 50% 축소, CS 기준 +15점 상향합니다.

**Circuit Breaker Level 2 (일일 손실 -5% 도달).** 전 포지션 즉시 청산, DESK 2 당일 완전 비활성화, 익일 TIER 1단계 하향 평가합니다.

**Circuit Breaker Level 3 (주간 손실 -10% 도달).** 다음 주 전체 비활성화, CEO 수동 재개 승인 필요합니다.

## Part 9. 백테스트 및 검증 프레임워크

### 9.1 백테스트 엔진 요구사항

백테스트 엔진은 실제 운영과 동일한 Layer 0~4 파이프라인을 사용하되, Layer 0을 히스토리컬 데이터로 대체합니다. 데이터 소스는 분봉 데이터(v4_minute_bar, 4.33M rows), 일봉 데이터, VI 이력 데이터, 업종 데이터(v4_sector_price), 뉴스 이력(존재 시)입니다.

슬리피지 시뮬레이션은 기본 0.1%이며, TIER별 추가 슬리피지(TIER 4: +0.05%, TIER 5: +0.1%)를 적용합니다. 수수료는 편도 0.015%(증권사 수수료) + 매도 시 0.18%(거래세, 2025년 기준)를 적용합니다.

### 9.2 검증 프로토콜

**Phase 1 — 개별 전략 백테스트.** 각 전략을 독립적으로 최소 1년(250 거래일) 백테스트합니다. 합격 기준은 기대값(E) > 0.5%, 승률 > 45%, Profit Factor > 1.3, Calmar Ratio > 1.5, 최대 연속 손실 < 5회입니다.

**Phase 2 — 복합 엔진 백테스트.** 7개 전략을 동시에 운영하는 복합 시뮬레이션을 1년간 실행합니다. 합격 기준은 월간 수익 > +5%, 일일 최대 손실 < -5%, Sharpe Ratio > 1.5, 자본 활용률 > 60%입니다.

**Phase 3 — Walk-Forward 검증.** 6개월 훈련 + 2개월 검증을 슬라이딩 윈도우로 실행합니다. 검증 구간에서도 Phase 2 합격 기준의 80% 이상을 달성해야 합니다.

**Phase 4 — A/B 비교.** 기존 DESK 2 단일 전략 대비 새 7엔진 구조의 성과를 동일 기간에서 비교합니다. 새 구조가 기존 대비 수익률 +20%p 이상, 최대 낙폭(MDD) -5%p 이상 개선되어야 합니다.

**Phase 5 — Mock Trading.** 실시간 데이터로 2주간 모의 매매를 실행합니다. 실제 주문은 전송하지 않되, 체결 시뮬레이션은 실시간 호가 기반으로 수행합니다.

## Part 11. 구현 지시서 (Cursor Tasks)

### Task 1: Layer 0 + 데이터 모델 (예상 3~4시간)

Layer 0의 5개 컴포넌트(TickCollector, BarBuilder, IndicatorEngine, NewsCollector, OrderBookCollector)와 models/ 디렉터리의 5개 데이터 모델을 구현합니다. Redis 연결 설정 및 채널 구조를 확립합니다. 완료 기준: 실시간 데이터 수신 시뮬레이션으로 TickEvent → BarEvent → Indicator 파이프라인이 1ms 이내 지연으로 동작합니다.

### Task 2: Layer 1 — Discovery Conditions (예상 5~6시간)

BaseCondition 추상 클래스와 7개 Condition 구현체를 개발합니다. 각 Condition의 scan(), score(), emit() 메서드를 구현합니다. DiscoveryManager가 7개 Condition을 병렬 실행하고 DiscoverySignal을 Redis Stream으로 발행합니다. 완료 기준: 히스토리컬 데이터 1일분을 입력하면 Condition별 발굴 종목과 DESK 점수가 출력됩니다.

### Task 3: Layer 2 — Strategy Engines (예상 5~6시간)

BaseStrategy 추상 클래스와 7개 Strategy 구현체를 개발합니다. evaluate(), generate_signal(), update(), manage_position() 메서드를 구현합니다. StrategyManager가 DiscoverySignal을 적합도 매트릭스에 따라 전략에 라우팅합니다. 완료 기준: DiscoverySignal을 입력하면 CS 계산 및 TradeSignal 생성이 정상 동작합니다.

### Task 4: Layer 3 — Orchestration (예상 4~5시간)

CompositeScorer, PriorityRanker, CapitalAllocator, RelayManager, ConflictResolver, WaitQueue, RegimeDetector, Orchestrator를 구현합니다. 500ms 메인 루프에서 전체 의사결정 파이프라인이 실행됩니다. 완료 기준: 복수 TradeSignal 입력 시 복합 점수 기반 우선순위 결정, 자본 배분, 충돌 해결이 정상 동작합니다.

### Task 5: Layer 4 + TIER + Risk (예상 4~5시간)

OrderManager, PositionTracker, ExitManager, SlippageMonitor, TradeLogger를 구현합니다. TierCalculator, CapitalTracker, CompoundingEngine을 구현합니다. HardKill, SoftKill, CircuitBreaker, RiskManager를 구현합니다. 완료 기준: ExecutionOrder 입력 시 모의 주문 전송, 포지션 추적, 청산 실행, 리스크 검사가 정상 동작합니다.

### Task 6: 상태 머신 + 모니터링 (예상 3~4시간)

TickerStateMachine, StrategyStateMachine, SystemState를 구현합니다. Dashboard, Alerter, DailyReporter를 구현합니다. 완료 기준: 종목 상태 전이(IDLE→DISCOVERED→...→COOLDOWN)가 정확히 추적되고, 대시보드 데이터가 실시간 갱신됩니다.

### Task 7: 백테스트 + 검증 (예상 6~8시간)

HistoricalDataLoader, BacktestEngine, WalkForward, ABComparator를 구현합니다. 5단계 검증 프로토콜(개별 전략 → 복합 → Walk-Forward → A/B → Mock)을 실행합니다. 완료 기준: 기존 DESK 2 대비 새 7엔진 구조의 성과 비교 보고서가 생성됩니다.

### Task 8: 통합 테스트 + End-to-End (예상 4~5시간)

전체 Layer 0→1→2→3→4 파이프라인을 연결하여 E2E 시뮬레이션을 실행합니다. 히스토리컬 데이터 1주일분으로 전체 시스템을 가동하여 일일 보고서 5개를 생성합니다. 완료 기준: 5일간 시뮬레이션 결과가 Phase 2 합격 기준을 충족합니다.

총 예상 소요: 34~42시간 (병렬 작업 시 15~20시간)
