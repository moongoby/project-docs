## 4. 저장 용량 추정

### 4-1. 뉴스 제목 (title only)

| 항목 | 수치 |
|------|------|
| 1건당 크기 | ~700 bytes (제목+메타데이터+종목코드) |
| 하루 뉴스+공시 건수 | 2,000~5,000건 (15개 매체 + 5개 공시 채널) |
| **일일 용량** | **1.4~3.5 MB** |
| **월간 용량** | **30~75 MB** |
| **연간 용량** | **360~900 MB** |
| 인덱스 포함 (×1.5) | **540 MB ~ 1.35 GB / 년** |

### 4-2. 뉴스 본문 (title + body)

| 항목 | 수치 |
|------|------|
| 1건당 본문 크기 | ~2~5 KB |
| 하루 전체 수집 시 | 4~25 MB |
| **월간 용량** | **120~750 MB** |
| **연간 용량** | **1.4~9 GB** |

### 4-3. 선택적 수집 시나리오 (권장)

| 시나리오 | 대상 | 일 건수 | 일 용량 | 연 용량 |
|----------|------|---------|--------|--------|
| A. 공시만 | 코드 F,G,H,I,N | ~200~500건 | ~200 KB | ~50 MB |
| B. 공시 + 종목관련 뉴스 | 공시 + iscd 있는 뉴스 | ~500~1,500건 | ~1 MB | ~250 MB |
| C. 전체 제목 | 모든 뉴스+공시 | ~3,000~5,000건 | ~3 MB | ~750 MB |
| D. 전체 제목+본문 | 위 + 본문 | ~3,000~5,000건 | ~15 MB | ~4.5 GB |

### 4-4. 현재 서버 여유 공간

| 항목 | 수치 |
|------|------|
| 디스크 전체 | 99 GB |
| 사용 중 | 84 GB (89%) |
| **여유** | **~11 GB** |
| 현재 DB 크기 | 13 GB |
| 분봉 테이블 (최대) | 월 ~1.1 GB |

> **주의**: 여유 공간 11GB에서 분봉 데이터가 월 ~1GB씩 증가 중.
> 시나리오 D(전체+본문)는 디스크 부족 위험. **시나리오 B (공시+종목뉴스 제목)** 권장.

## 5. 기존 코드 연동 가능성

### 5-1. 트레이딩 로직의 뉴스 플래그 (현재 하드코딩)

| 파일 | 사용 필드 | 현재 상태 |
|------|-----------|-----------|
| `indicator_cache.py:36-38` | `has_news`, `news_category`, `has_bad_news` | 항상 `False` / `""` |
| `c1_gap_discovery.py:72` | `has_news` → +15점 | 항상 0점 |
| `c3_vi_explosion.py:67` | `has_news` → +15점 | 항상 0점 |
| `c7_oversold_rebound.py:82` | `has_bad_news` 없으면 +10점 | 항상 10점 |

**뉴스 수집 시**: indicator_cache에 실시간 뉴스/공시 데이터를 주입하면 발굴 스코어링 정확도가 향상됨.

### 5-2. 필요한 구현 작업

1. **kis_api_registry.py**: `FHKST01011800` (종합 시황_공시) 엔드포인트 등록
2. **DB 테이블**: `v4_news_items` 생성 (제목, 출처, 종목코드, 분류)
3. **수집기**: `backend/app/services/data/news_collector.py`
4. **스케줄러**: 장중 5분 간격 수집 (cron 또는 APScheduler)
5. **indicator_cache 연동**: 종목별 뉴스 플래그 업데이트
