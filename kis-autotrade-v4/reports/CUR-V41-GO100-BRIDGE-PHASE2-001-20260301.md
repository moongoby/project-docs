### 3.2 시나리오 1 — 정상 매매 + 메모리 적재

**흐름**:
1. `GET /api/go100/bridge/risk/status` → `kill_switch_active=False` 확인 → 진입 허용
2. 삼성전자(005930) 가상 진입 @ 75,000원 × 10주 → 청산 @ 76,875원 (+2.5%)
3. SK하이닉스(000660) 가상 진입 @ 180,000원 × 4주 → 청산 @ 182,700원 (+1.5%)
4. 각 청산 직후 `POST /api/go100/bridge/memory/log` → `go100_user_memory` Append

### 3.3 시나리오 2 — 킬스위치 Mock → 진입 차단

**흐름**:
1. `unittest.mock.AsyncMock`으로 `get_risk_status()` Mock 주입 → `kill_switch_active=True` 반환
2. Mock 리스크 응답: `daily_pnl_pct=-3.5%`, `halt_reason="DAILY_LOSS_LIMIT_EXCEEDED (Mock)"`
3. 매매 루프가 `kill_switch_active=True` 감지 → **"[Halt] 킬스위치 감지 → 신규 진입 전면 차단"** 출력
4. 삼성전자, SK하이닉스 2건 모두 매수 Skip 확인
5. 추가 검증: `get_risk_status()` 정확히 1회 호출 확인

**Mock 방식 선택 이유**: 실제 GO100 DB를 변경하지 않고도 킬스위치 상태를 시뮬레이션.
`kill_switch_active` 플래그를 DB에서 직접 변경하면 실계좌 리스크 발생 → Mock 처리가 안전.

## 5. Task B: backtest_engine_v2.py 브릿지 통합 스텁

### 5.1 추가 내용

```
BacktestConfig.enable_go100_bridge: bool = False   ← 비파괴적 플래그

BacktestEngineV2:
 ├── _bridge_check_risk_before_entry()  ← 삽입점 A: 주문 전 킬스위치 확인
 └── _bridge_log_trade_memory(trade)   ← 삽입점 B: 청산 후 에피소드 적재
```

### 5.2 활성화 방법 (Phase 3 시점)

**삽입점 A** (`_run_entry_signals` 내부):
```python
# ── [브릿지 삽입점 A] 주문 직전 킬스위치 확인
if self.config.enable_go100_bridge:
    allowed = await self._bridge_check_risk_before_entry()
    if not allowed:
        logger.warning("[Bridge] 킬스위치 — %s 전 종목 진입 차단", trade_date)
        return
```

**삽입점 B** (`_check_positions` 내부, `self._trade_log.append(...)` 직후):
```python
# ── [브릿지 삽입점 B] 청산 후 에피소드 메모리 적재
if self.config.enable_go100_bridge:
    await self._bridge_log_trade_memory(self._trade_log[-1])
```

### 5.3 설계 원칙

| 속성 | 내용 |
|------|------|
| **비파괴성** | `enable_go100_bridge=False`(기본값) → 기존 백테스트 로직 100% 유지 |
| **Fail-Open** | `_bridge_check_risk_before_entry()` — 브릿지 오류 시 True 반환(진입 허용) |
| **Best-Effort** | `_bridge_log_trade_memory()` — 메모리 적재 실패는 매매 차단 안 함 |
| **지연 import** | `enable_go100_bridge=False` 시 httpx 불필요한 의존성 미로드 |
