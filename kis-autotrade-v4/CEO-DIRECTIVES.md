## 1. 사고방식 원칙

### D-001 단순 사고 금지
- "하나를 던지면 10을 생각하고 연구해서 반영하라"
- 단일 변수, 단일 시점, 단일 관점 분석은 불충분
- 복합계, 다층 구조, 다시점 분석이 기본

### D-002 본질은 수급이다
- 모든 가격 움직임의 본질은 수급(매수·매도 세력의 흐름)
- 스마트머니(외국인·기관)는 며칠에 걸쳐 소규모로 매집
- 개인 투자자도 무시 금지 – 텔레그램, 유튜브, 커뮤니티로 정보 전파 빠름
- 수급 분석은 D-1 스냅샷이 아니라 D-20 → D-1 궤적으로 봐야 함

### D-003 DESK의 본질
- DESK는 "오늘 오를 종목 10개를 맞히는 것"이 아니다
- DESK는 "오를 만한 종목을 풀로 관리하고, 전략 카드가 타이밍을 기다리는 것"
- DESK가 타이밍을 정확하게 알 필요 없음
- 풀에 넣어두고 전략이 트리거를 감지하면 진입
- 핵심 전환: 정밀도(precision) → 리콜(recall) + 풀 체류 관리

### D-004 일봉 상승 전조 패턴
- 급등 종목 전형 패턴: 강한 수급 유입 → 약간의 눌림(거래대금↓) → 횡보/하락 → 지지 → 반등
- 눌림매매, 3·5일선 터치, 박스 돌파, 신고가 돌파는 모두 같은 원리의 변형
- 2~4일 추적 대기도 유효한 발굴
- "강하게 오른 놈이 또 오른다" = L3+X9가 작동하는 이유

### D-005 신고가 돌파 매매
- 최고가 초과 시 매물대 소멸 → 매도 심리 감소 → 적은 매수세로 급등
- 모든 보유자 수익 상태 → 매도 압력↓, 추가 매수 유도
- 공매도 숏커버링 + FOMO 추격 매수
- 거래량 없는 가짜 돌파 주의 → 거래량 급증 필수 확인

### D-006 NEW 종목도 과거가 있다
- TOP-20 첫 등장 종목도 D-180 ~ D-30에 이미 시그널 존재
- 저점 횡보 → 수급 유입 → 이평선 수렴 → 정배열 → 급등의 생애주기
- DESK5→4→3 파이프라인 작동 시 사전 포착 가능
- 3년치 일봉(ohlcv_daily 261만 rows)으로 역추적 필수

### D-010: DESK2 멀티-컨디션 엔진 (2026-02-28 CEO 승인)

#### 핵심 원칙
1. DESK2 = N개 컨디션 모듈 × M개 전략 매칭 (1:N)
2. 하루 동안 발생하는 모든 수익 기회를 포착 (DCS 일일합산)
3. 전략은 5축(시간대/시장상태/변동성/순위/보유시간)으로 ON/OFF
4. 컨디션 자체에 생애주기(A/B/C 등급) 적용, 20거래일 주기 리밸런싱
5. 비대칭 수익(PF ≥ 1.3) 기준 채택, 승률보다 PF 우선

#### 7대 가설
- H-001: 단일 스코어카드 한계 → 유형별 컨디션 분리
- H-002: 1:N 매칭 → DCS 일일합산
- H-003: 5축 ON/OFF → 손실구간 제거
- H-004: 비대칭 수익 > 승률
- H-005: RSI 30~50 최강 필터
- H-006: NEW = 장중 1분봉만 가능
- H-007: 컨디션 생애주기 (A/B/C 등급)

#### 컨디션 목록
C1(상한가예상), C2(전일상한가), C3(시초가강세), C4(장중1파급등), C5(테마동시급등), C6(종가강세), C7(NEW탐지)

#### 5축 운영 마스크
- 축1 시간대(T1~T6), 축2 시장상태(BULL/FLAT/BEAR), 축3 변동성(LOW/MID/HIGH), 축4 순위(TOP/MID/LOW), 축5 보유시간(SCALP/SHORT/MID/HOLD)

#### 등급 체계
- A(실전 40%): DCS≥+2%, 양일≥60%
- B(소규모 10%): DCS +0.5~2%, 양일≥50%
- C(시뮬 0%): DCS<+0.5% 또는 양일<50%

Phase A(D4/D6/D7) → Phase E(5축 분해) → Phase C(D3/S1/S2) → Phase D(NEW) → 설계서 → 구현 → 시뮬 → 실전

### 4-9. CEO 보고 규칙 (REPORT-001) — 위반 시 미보고 처리

작업 완료 후 CEO에게 보고할 때:

1. **반드시 git push 먼저 완료**한다
2. **서버 로컬 경로로 보고하지 않는다**
   - ❌ "보고서: /root/project-docs/go100/reports/CUR-GO100-P5-3-..."
   - ❌ "저장 완료했습니다"
   - ❌ "/root/project-docs에 push 했습니다"
3. **반드시 GitHub 브라우저 URL로 보고한다**
   - ✅ https://github.com/moongoby/project-docs/blob/master/go100/reports/CUR-GO100-P5-3-PORTFOLIO-OPTIMIZER-001-20260227.md
   - ✅ https://github.com/moongoby/project-docs/blob/master/kis-autotrade-v4/reports/DESK2-VALIDATION-ENGINE-001-20260228.md

4. **보고 형식 (필수)**:

보고서: https://github.com/moongoby/project-docs/blob/master/{프로젝트}/reports/{파일명}  
커밋: https://github.com/moongoby/project-docs/commit/{SHA}  
HANDOVER: https://github.com/moongoby/project-docs/blob/master/{프로젝트}/HANDOVER.md  
HTTP: 200 확인 완료

5. **URL이 실제로 접근 가능한지 확인 후 보고**:
```bash
# push 후 반드시 실행
HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" \
  "https://raw.githubusercontent.com/moongoby/project-docs/master/{프로젝트}/reports/{파일명}")
echo "HTTP: $HTTP_CODE"
# 200이 아니면 보고하지 말고 원인 파악
```
- push 안 하고 "작성 완료"로 보고하면 미완료 처리
- 서버 경로만 적고 GitHub URL 없으면 미보고 처리

## 9-10. 지시서 자동화 시스템 규칙 (신규, 2026-03-08)

### 핵심 원칙
- bridge.py(서버 211)는 이 매니저 대화창을 실시간 감시한다.
- 매니저가 `>>>DIRECTIVE_START ~ >>>DIRECTIVE_END` 블록을 대화창에 출력하면, bridge.py가 자동으로 pending 폴더에 저장한다.
- **CEO에게 "지시서를 전달해 주세요"라고 요청하는 것은 절대 금지한다.**
- 매니저는 지시서를 출력하기만 하면 된다. 전달·저장·실행은 모두 자동이다.

### 자동화 흐름
```
CEO 지시 → 매니저 분석 → 대화창에 지시서 출력
  → bridge.py 자동 감지 → pending/ 자동 저장
  → auto_trigger.sh 10초 폴링 → Cursor AI 실행
  → 결과 보고 → DB 기록 → 교차 검증
```

### 매니저가 해야 할 것
1. CEO 지시를 분석한다.
2. `>>>DIRECTIVE_START ~ >>>DIRECTIVE_END` 지시서를 대화창에 출력한다.
3. 작업 완료 보고를 확인한다.
4. CEO에게 결과를 보고한다.

### 매니저가 하지 말아야 할 것
1. ❌ "이 지시서를 전달해 주세요"
2. ❌ "이 내용을 bridge에 넣어 주세요"
3. ❌ "CEO님이 직접 실행해 주세요"
4. ❌ 지시서 블록 없이 구두로만 작업 요청
