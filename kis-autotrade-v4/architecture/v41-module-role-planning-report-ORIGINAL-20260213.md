## 2. LAYER 0 — System Orchestrator (사장실)

```
╔══════════════════════════════════════════════════════════════════════════╗

╠══════════════════════════════════════════════════════════════════════════╣

║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║

║  │                                                                  │     ║

║  │                                                                  │     ║
║  │    class StateTransitionValidator:                               │     ║
║  │                                                                  │     ║

║  │          ("price_poller_live",                                   │     ║

║  │          ("position_manager_healthy",                            │     ║

║  │          ("regime_determined",                                   │     ║
║  │           self.regime.score is not None),                       │     ║
║  │          ("calendar_checked",                                    │     ║
║  │           self.calendar.adjustment is not None),                │     ║
║  │          ("data_quality_ok",                                     │     ║
║  │           self.quality.grade >= GRADE_B),                       │     ║

║  │            allowed=False,                                        │     ║
║  │            fallback_state="DEGRADED_READY",                     │     ║
║  │            failed_checks=failed                                  │     ║
║  │          )                                                       │     ║
║  │        return TransitionResult(allowed=True)                     │     ║
║  │                                                                  │     ║
║  │  각 전이별 검증기가 별도 메서드로 존재                          │     ║
║  │  검증 실패 시 자동으로 fallback 상태로 전환 + 알림             │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║

║  │                                                                  │     ║
║  │  무엇: 시스템이 살아있다는 증거를 주기적으로 기록               │     ║
║  │                                                                  │     ║
```

```
╠══════════════════════════════════════════════════════════════════════════╣
║                                                                          ║

║  ═══════════════════════════════════════════════════════════             ║

║  │    점수화:                                                       │     ║
║  │      15 미만 → 100점 (안정)                                    │     ║
║  │      15~25 → 비례                                               │     ║
║  │      25 초과 → 0점 (공포)                                      │     ║
║  │    ★ VKOSPI 데이터 없으면: 다른 5개 지표로만 계산              │     ║
║  │      (가중치 재분배)                                             │     ║
║  │                                                                  │     ║
║  │  최종 regime_score:                                               │     ║
║  │    가중 평균 (현재 균등 가중, 향후 Adaptive에서 조정 가능)      │     ║
║  │    regime_score = 0~100 연속값                                   │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 2: 레짐 라벨 매핑                                          │     ║
║  │                                                                  │     ║
║  │  regime_score → 5대 레짐 라벨 변환                               │     ║
║  │                                                                  │     ║
║  │    80~100: STRONG_TREND_UP    (강한 상승 추세)                   │     ║

║  │     0~19:  STRONG_TREND_DOWN  (강한 하락 추세)                   │     ║
║  │                                                                  │     ║
║  │  각 레짐이 시스템에 미치는 영향:                                 │     ║

║  │    - 손절/익절 폭 조정                                          │     ║
║  │    - 진입 score 하한 변경                                       │     ║
║  │    - 현금 비중 조정                                              │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 3: ★ V4.1 레짐 전환 히스테리시스                          │     ║
║  │                                                                  │     ║
║  │  무엇: 레짐 라벨이 너무 자주 바뀌지 않도록 전환에               │     ║
║  │        관성을 부여하는 장치                                      │     ║
║  │                                                                  │     ║
║  │  왜 필요한가:                                                    │     ║
║  │    월요일: MILD_UP → 화요일: SIDEWAYS → 수요일: MILD_UP       │     ║
║  │    이렇게 진동하면 전략 파라미터가 매일 바뀌어 혼란스럽다.      │     ║
║  │    실제 시장에서 레짐은 며칠~몇 주 단위로 바뀌는 것이 정상.     │     ║
║  │                                                                  │     ║
║  │  구현 기획:                                                      │     ║
║  │                                                                  │     ║
║  │    class RegimeTransitionManager:                                │     ║
║  │                                                                  │     ║
║  │      def __init__(self):                                        │     ║
║  │        self.current_regime = "SIDEWAYS"                         │     ║
║  │        self.pending_regime = None                                │     ║
║  │        self.pending_days = 0                                     │     ║
║  │                                                                  │     ║
║  │      def update(self, raw_regime: str) -> str:                  │     ║
║  │        if raw_regime == self.current_regime:                    │     ║
║  │          self.pending_regime = None                              │     ║
║  │          self.pending_days = 0                                   │     ║
║  │          return self.current_regime                              │     ║
║  │                                                                  │     ║
║  │        # 새 레짐이 감지됨                                       │     ║
║  │        if raw_regime == self.pending_regime:                    │     ║
║  │          self.pending_days += 1                                  │     ║
║  │        else:                                                     │     ║
║  │          self.pending_regime = raw_regime                        │     ║
║  │          self.pending_days = 1                                   │     ║
║  │                                                                  │     ║
║  │        # 비대칭 기준                                             │     ║
║  │        required_days = self._get_required_days(                 │     ║
║  │          self.current_regime, raw_regime                        │     ║
║  │        )                                                         │     ║
║  │                                                                  │     ║
║  │        if self.pending_days >= required_days:                   │     ║
║  │          self.current_regime = raw_regime                        │     ║
║  │          self.pending_regime = None                              │     ║
║  │          self.pending_days = 0                                   │     ║
║  │                                                                  │     ║
║  │        return self.current_regime                                │     ║
║  │                                                                  │     ║
║  │      def _get_required_days(self, current, new):                │     ║
║  │        regime_order = {                                          │     ║
║  │          "STRONG_TREND_DOWN": 0,                                │     ║
║  │          "MILD_TREND_DOWN": 1,                                  │     ║
║  │          "SIDEWAYS": 2,                                         │     ║
║  │          "MILD_TREND_UP": 3,                                    │     ║
║  │          "STRONG_TREND_UP": 4,                                  │     ║
║  │        }                                                         │     ║
║  │        going_up = regime_order[new] > regime_order[current]     │     ║

║  │                                                                  │     ║
```

```
## 9. LAYER 5-A — Risk Manager 2계층 (리스크관리본부)

```
╔══════════════════════════════════════════════════════════════════════════╗
║  RISK MANAGER 2계층 — 세부 역할 및 기획                                  ║
╠══════════════════════════════════════════════════════════════════════════╣
║                                                                          ║

║                                                                          ║

║    이 모듈이 장애를 일으키면:                                           ║
║      - 신규 진입 검사도 안 되고                                        ║

║                                                                          ║

║  │                                                                  │     ║
║  │  ─────────────────────────────────────────────────              │     ║
║  │                                                                  │     ║

║  │                                                                  │     ║
║  │      # 60초 이상이면 보수적 청산 시도                           │     ║
║  │      if position.price_staleness > 60_000:                      │     ║
║  │        return CriticalAction(                                    │     ║
║  │          action="CONSERVATIVE_SELL",                             │     ║
║  │          reason="가격 불명 60초 초과",                          │     ║
║  │          urgency="HIGH"                                         │     ║
║  │        )                                                         │     ║
║  │                                                                  │     ║
║  │      # 청산도 실패하면 대표님 즉시 알림                         │     ║
║  │      # "수동 대응 필요: {종목} 가격 조회 불가 + 청산 실패"     │     ║
║  │                                                                  │     ║
║  │  ─────────────────────────────────────────────────              │     ║
║  │                                                                  │     ║
║  │  ★ 설계 핵심 원칙:                                               │     ║
║  │    - strategy, data_provider, fund_commander에 의존하지 않음    │     ║
║  │    - critical_risk_config만 참조 (다른 설정 파일 장애 격리)     │     ║
║  │    - 가격 조회는 PricePoller 캐시에서 읽되,                     │     ║
║  │      캐시도 실패하면 "가격 불명 = 위험" 원칙 적용              │     ║
║  │    - 이 커널이 죽는 상황 = 시스템 전체 즉시 정지 + 알림       │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ═══════════════════════════════════════════════════════════             ║
║                                                                          ║
║  ■ 계층 2: Full RiskManager (정교한 검사)                               ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  정상 운영 시 활성. 장애 시 비활성 (CriticalRiskKernel만 잔존) │     ║
║  │                                                                  │     ║
║  │  ─────────────────────────────────────────────────              │     ║
║  │                                                                  │     ║
║  │  기능 1: pre_trade_check (매수 전 종합 검사)                    │     ║
║  │                                                                  │     ║
║  │  async def pre_trade_check(self, signal, bet_amount) -> Check:  │     ║
║  │                                                                  │     ║
║  │    checks = []                                                   │     ║
║  │                                                                  │     ║
║  │    # [1] 최대 동시 포지션 수 제한                               │     ║
║  │    open_count = await count_open_positions(user_id)             │     ║
║  │    if open_count >= self.config.max_positions:  # 기본: 5       │     ║
║  │      checks.append(("max_positions", False,                     │     ║
║  │                      f"최대 포지션 수 초과: {open_count}"))     │     ║
║  │                                                                  │     ║
║  │    # [2] 1종목 1포지션 강제                                     │     ║
║  │    existing = await get_position(user_id, signal.ticker)        │     ║
║  │    if existing:                                                  │     ║
║  │      checks.append(("duplicate_position", False,                │     ║
║  │                      "이미 보유 중인 종목"))                    │     ║
║  │                                                                  │     ║
║  │    # [3] 당일 재매수 규칙 (ReentryGuard)                        │     ║
║  │    reentry = await reentry_guard.check_reentry(                 │     ║
║  │      user_id, signal.ticker, signal                             │     ║
║  │    )                                                             │     ║
║  │    if not reentry.allowed:                                      │     ║
║  │      checks.append(("reentry_blocked", False, reentry.reason)) │     ║
║  │                                                                  │     ║
║  │    # [4] 자금 가용성 확인                                       │     ║
║  │    if bet_amount > fund_pool.available:                         │     ║
║  │      checks.append(("insufficient_funds", False,                │     ║
║  │                      f"가용 자금 부족: {fund_pool.available}")) │     ║
║  │                                                                  │     ║
║  │    # [5] 데스크 한도 확인                                       │     ║
║  │    if not fund_pool.can_allocate(signal.desk_id, bet_amount):  │     ║
║  │      checks.append(("desk_limit", False,                        │     ║
║  │                      "데스크 자금 한도 초과"))                  │     ║
║  │                                                                  │     ║
║  │    # [6] 데이터 품질 확인                                       │     ║
║  │    if data_quality.grade == GRADE_D:                             │     ║
║  │      checks.append(("data_quality", False,                      │     ║
║  │                      "데이터 품질 최하 — 매매 불가"))          │     ║
║  │                                                                  │     ║
║  │    # [7] 종목별 캘린더 제한 확인                                 │     ║
║  │    if calendar.is_restricted(signal.ticker, today):             │     ║
║  │      checks.append(("calendar_restricted", False,               │     ║
║  │                      "캘린더 제한 종목"))                       │     ║
║  │                                                                  │     ║
║  │    failed = [c for c in checks if not c[1]]                     │     ║
║  │    if failed:                                                    │     ║
║  │      return CheckResult(passed=False, reasons=failed)           │     ║
║  │    return CheckResult(passed=True)                               │     ║
║  │                                                                  │     ║
║  │  ─────────────────────────────────────────────────              │     ║
║  │                                                                  │     ║
║  │  기능 2: 예약금 관리                                             │     ║
║  │                                                                  │     ║
║  │    pre_trade_check 통과 후:                                     │     ║
║  │      → 예약금 생성 (v4_reservations INSERT, state=RESERVED)    │     ║
║  │      → fund_pool.allocate() 호출                               │     ║
║  │      → 주문 제출 시 state → ORDER_SUBMITTED                   │     ║
║  │      → 체결 시 state → FILLED, fund_pool reserved→invested   │     ║
║  │      → 실패 시 state → FAILED/CANCELLED, fund_pool release    │     ║
║  │      → 5분 만료 시 state → EXPIRED, fund_pool release         │     ║
║  │                                                                  │     ║
║  │  ─────────────────────────────────────────────────              │     ║
║  │                                                                  │     ║
║  │  기능 3: 레짐/무드 연동 리스크 파라미터 조정                     │     ║
║  │                                                                  │     ║
║  │    레짐에 따라:                                                  │     ║
║  │      STRONG_DOWN → max_positions 0으로 설정 (신규 진입 차단)   │     ║
║  │      MILD_DOWN → max_positions 2로 축소                        │     ║
║  │      SIDEWAYS → max_positions 3                                 │     ║
║  │      MILD_UP/STRONG_UP → max_positions 5 (기본)                │     ║
║  │                                                                  │     ║
║  │    장중 mood 급락 시:                                            │     ║
║  │      mood_score 10+ 하락 → trailing_stop 1% 강화              │     ║
║  │      mood_score 20+ 하락 → 손실 포지션 청산 검토               │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ═══════════════════════════════════════════════════════════             ║
║                                                                          ║
║  ■ 2계층 장애 시나리오별 대응                                            ║
║                                                                          ║
║  ┌─────────────────────┬─────────────────────────────────────────┐     ║
║  │ 시나리오             │ 대응                                      │     ║
║  ├─────────────────────┼─────────────────────────────────────────┤     ║
║  │ 둘 다 정상          │ Full이 신규 진입 검사                     │     ║
║  │                     │ CRK가 기존 포지션 손절 감시              │     ║
║  │                     │ → 정상 운영                               │     ║
║  │                     │                                           │     ║
║  │ Full 장애,          │ 신규 진입 전면 차단                       │     ║
║  │ CRK 정상            │ CRK가 기존 포지션 손절/강제청산 계속     │     ║
║  │                     │ → "돈은 잃지 않는다"                      │     ║
║  │                     │ → 대표님 알림                             │     ║
║  │                     │                                           │     ║
║  │ Full 정상,          │ ★ 이 상황은 발생하면 안 됨               │     ║
║  │ CRK 장애            │ CRK는 position_manager 내부 내장이므로   │     ║
║  │                     │ CRK가 죽으면 position_manager도 죽은 것  │     ║
║  │                     │ → 시스템 전체 즉시 정지                   │     ║
║  │                     │ → 대표님 즉시 알림 (최고 긴급)           │     ║
║  │                     │ → 수동 대응 필요                          │     ║
║  │                     │                                           │     ║
║  │ 둘 다 장애          │ → 시스템 전체 즉시 정지                   │     ║
║  │                     │ → 대표님 즉시 알림 (최고 긴급)           │     ║
║  │                     │ → 수동 대응 필요                          │     ║
║  └─────────────────────┴─────────────────────────────────────────┘     ║
║                                                                          ║
║  ■ 입력: 매매 신호, FundPool 상태, 포지션 목록, RegimeContext,          ║
║         CalendarAdj, DataQualityGrade, 실시간 가격                       ║
║  ■ 출력: CheckResult(통과/거부), CriticalAction(강제청산 명령)          ║

║                                                                          ║

```

## 10. LAYER 5-B — Order Executor (주문 집행팀)

```
╔══════════════════════════════════════════════════════════════════════════╗
║  ORDER EXECUTOR — 세부 역할 및 기획                                      ║
╠══════════════════════════════════════════════════════════════════════════╣
║                                                                          ║
║  ■ 한 줄 요약                                                           ║
║    "리스크 체크를 통과한 매매 신호를 KIS API를 통해 실제 증권사에       ║
║     주문을 넣고, 체결 결과를 확인하여 시스템에 반영하는 주문 집행팀"   ║
║                                                                          ║
║  ═══════════════════════════════════════════════════════════             ║
║                                                                          ║
║  ■ 왜 필요한가                                                          ║
║                                                                          ║
║    시스템 내부에서 "삼성전자 25만원어치 매수"라는 결정이 나와도        ║
║    실제로 한국투자증권(KIS) API를 호출하여 주문을 넣어야 합니다.       ║
║                                                                          ║
║    이 과정에서:                                                          ║
║      - API 호출 실패, 타임아웃, 거부 처리                               ║
║      - 주문번호 수신 및 기록                                            ║
║      - 체결 확인 (전량 체결/부분 체결/미체결)                          ║
║      - 체결가와 주문가의 차이(슬리피지) 기록                          ║
║      - 예약금 상태 전환 (ORDER_SUBMITTED → FILLED/FAILED)             ║
║                                                                          ║
║    이 모든 것을 안전하고 추적 가능하게 처리하는 것이                   ║
║    Order Executor의 역할입니다.                                         ║
║                                                                          ║
║  ═══════════════════════════════════════════════════════════             ║
║                                                                          ║
║  ■ 세부 역할 분해 (6가지)                                               ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 1: 매수 주문 실행                                          │     ║
║  │                                                                  │     ║
║  │  async def execute_buy(self, signal, bet_amount,                │     ║
║  │                         reservation_id, order_request_id):      │     ║
║  │                                                                  │     ║
║  │    # 1) 주문 수량 계산                                          │     ║
║  │    current_price = price_poller.get(signal.ticker)              │     ║
║  │    quantity = bet_amount // current_price                       │     ║
║  │    if quantity == 0:                                             │     ║
║  │      await update_reservation(reservation_id, 'RELEASED')      │     ║
║  │      return ExecutionResult(success=False,                      │     ║
║  │                             reason="수량 0 — 금액 부족")       │     ║
║  │                                                                  │     ║
║  │    # 2) 예약금 상태 전환                                        │     ║
║  │    await update_reservation(reservation_id, 'ORDER_SUBMITTED')  │     ║
║  │                                                                  │     ║
║  │    # 3) KIS API 호출                                            │     ║
║  │    try:                                                          │     ║
║  │      await rate_limiter.acquire(priority='ORDER')               │     ║
║  │      kis_result = await kis_api.buy_order(                      │     ║
║  │        ticker=signal.ticker,                                    │     ║
║  │        quantity=quantity,                                       │     ║
║  │        order_type='MARKET'  # 시장가                           │     ║
║  │      )                                                           │     ║
║  │    except Timeout:                                               │     ║
║  │      await update_order_request(order_request_id,               │     ║
║  │                                  status='FAILED',               │     ║
║  │                                  reason='KIS API 타임아웃')    │     ║
║  │      await update_reservation(reservation_id, 'FAILED')        │     ║
║  │      return ExecutionResult(success=False)                      │     ║
║  │    except KISError as e:                                        │     ║
║  │      await update_order_request(order_request_id,               │     ║
║  │                                  status='REJECTED',             │     ║
║  │                                  reason=str(e))                 │     ║
║  │      await update_reservation(reservation_id, 'FAILED')        │     ║
║  │      return ExecutionResult(success=False)                      │     ║
║  │                                                                  │     ║
║  │    # 4) 주문 제출 성공 — 결과 기록                              │     ║
║  │    await update_order_request(order_request_id,                 │     ║
║  │      status='SUBMITTED',                                        │     ║
║  │      kis_order_no=kis_result.order_no                           │     ║
║  │    )                                                             │     ║
║  │                                                                  │     ║
║  │    # 5) 체결 확인 (별도 함수로 위임)                            │     ║
║  │    fill_result = await self.wait_for_fill(                      │     ║
║  │      kis_result.order_no, timeout=30                            │     ║
║  │    )                                                             │     ║
║  │    return fill_result                                            │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 2: 체결 확인 및 기록                                       │     ║
║  │                                                                  │     ║
║  │  async def wait_for_fill(self, order_no, timeout=30):           │     ║
║  │    """                                                           │     ║
║  │    주문 제출 후 체결될 때까지 대기.                              │     ║
║  │    시장가 주문은 대부분 즉시 체결되지만,                        │     ║
║  │    거래량 적은 종목은 시간이 걸릴 수 있음.                      │     ║
║  │    """                                                           │     ║
║  │    start = time.time()                                          │     ║
║  │    while time.time() - start < timeout:                         │     ║
║  │      status = await kis_api.check_order_status(order_no)       │     ║
║  │                                                                  │     ║
║  │      if status.is_filled:                                       │     ║
║  │        fill_latency = int((time.time() - start) * 1000)        │     ║
║  │        slippage = (status.fill_price - order_price)             │     ║
║  │                   / order_price * 100                           │     ║
║  │        await update_order_request(order_request_id,             │     ║
║  │          status='FILLED',                                       │     ║
║  │          fill_price=status.fill_price,                          │     ║
║  │          fill_qty=status.fill_qty,                              │     ║
║  │          fill_amount=status.fill_price * status.fill_qty,      │     ║
║  │          fill_latency_ms=fill_latency,                          │     ║
║  │          slippage_pct=slippage                                  │     ║
║  │        )                                                         │     ║
║  │        return FillResult(success=True, ...)                     │     ║
║  │                                                                  │     ║
║  │      if status.is_partial:                                      │     ║
║  │        # 부분 체결 처리 (잔여분 예약금 반환)                   │     ║
║  │        ...                                                       │     ║
║  │                                                                  │     ║
║  │      await asyncio.sleep(1)  # 1초 대기 후 재확인              │     ║
║  │                                                                  │     ║
║  │    # 타임아웃 — 미체결 주문 취소                                │     ║
║  │    await kis_api.cancel_order(order_no)                         │     ║
║  │    await update_order_request(order_request_id,                 │     ║
║  │      status='CANCELLED', reason='체결 대기 타임아웃')          │     ║
║  │    return FillResult(success=False)                              │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 3: 매도 주문 실행                                          │     ║
║  │                                                                  │     ║
║  │  매수와 유사하되 차이점:                                         │     ║
║  │    - 예약금 불필요 (이미 보유한 주식을 파는 것)                  │     ║
║  │    - 매도 완료 시 fund_pool에 자금 반환                          │     ║
║  │    - 포지션 상태를 CLOSED로 변경                                │     ║
║  │    - 실현 손익 계산 및 기록                                     │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 4: 매수 차단 플래그 관리                                    │     ║
║  │                                                                  │     ║
║  │  Orchestrator가 CLOSING 상태로 전환할 때:                        │     ║
║  │    order_executor.set_buy_blocked(True)                          │     ║
║  │                                                                  │     ║
║  │  이후 모든 execute_buy 호출은 즉시 거부:                        │     ║

```
## 12. LAYER 6 — Position Manager (포지션 감시탑)

```
╔══════════════════════════════════════════════════════════════════════════╗
║  POSITION MANAGER — 세부 역할 및 기획                                    ║
╠══════════════════════════════════════════════════════════════════════════╣
║                                                                          ║
║  ■ 한 줄 요약                                                           ║
║    "매수 후 보유 중인 모든 포지션을 실시간 감시하여                     ║
║     손절/익절/트레일링/승격/강제청산을 실행하는 포지션 감시탑.         ║
║     ★ 시스템에서 절대 죽으면 안 되는 모듈. CriticalRiskKernel 내장."  ║
║                                                                          ║
║  ═══════════════════════════════════════════════════════════             ║
║                                                                          ║
║  ■ 왜 "절대 죽으면 안 되는가"                                          ║
║                                                                          ║
║    매수 기능이 죽으면 → 기회를 놓칠 뿐 (돈을 잃지는 않음)             ║
║    분석 기능이 죽으면 → 신규 진입을 안 하면 됨                        ║
║    포지션 감시가 죽으면 → 보유 중인 주식의 손절이 안 됨               ║
║      → 주가가 -10%, -20% 빠져도 시스템이 모름                        ║
║      → 실제 자금 대량 손실                                             ║
║                                                                          ║
║    따라서 position_manager는:                                            ║
║      - 독립 프로세스로 분리 운영 (다른 모듈과 격리)                    ║
║      - CriticalRiskKernel을 내부에 내장                                ║
║      - fallback 청산 경로를 자체 보유                                  ║
║      - 다른 모듈이 전부 죽어도 이것만은 살아서 손절 실행              ║
║                                                                          ║
║  ═══════════════════════════════════════════════════════════             ║
║                                                                          ║
║  ■ 세부 역할 분해 (8가지)                                               ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 1: 포지션 실시간 감시 (check_positions)                    │     ║
║  │                                                                  │     ║
║  │  60초 사이클마다 호출 (사이클 내 첫 번째 단계):                 │     ║
║  │                                                                  │     ║
║  │  async def check_positions(self):                               │     ║
║  │    open_positions = await get_open_positions(user_id)           │     ║
║  │                                                                  │     ║
║  │    for position in open_positions:                              │     ║
║  │      cache_entry = price_poller.get(position.ticker)            │     ║
║  │      current_price = cache_entry['price']                       │     ║
║  │      staleness = now() - cache_entry['ts']                      │     ║
║  │                                                                  │     ║
║  │      # 1) CriticalRiskKernel 검사 (최우선)                     │     ║
║  │      critical = self.crk.check(position, current_price,         │     ║
║  │                                 staleness)                      │     ║
║  │      if critical:                                                │     ║
║  │        await self.execute_critical_action(critical)             │     ║
║  │        continue                                                  │     ║
║  │                                                                  │     ║
║  │      # 2) 트레일링 스톱 체크                                   │     ║
║  │      if current_price > position.peak_price:                    │     ║
║  │        position.peak_price = current_price  # 고점 갱신        │     ║
║  │      trailing_stop = position.peak_price * (                    │     ║
║  │        1 - position.trailing_stop_pct / 100                    │     ║
║  │      )                                                           │     ║
║  │      if current_price <= trailing_stop:                         │     ║
║  │        await self.sell(position, reason='trailing_stop')        │     ║
║  │        continue                                                  │     ║
║  │                                                                  │     ║
║  │      # 3) 목표 수익 도달 체크                                   │     ║
║  │      pnl_pct = (current_price - position.entry_price)           │     ║
║  │                / position.entry_price * 100                     │     ║
║  │      if pnl_pct >= position.target_profit_pct:                  │     ║
║  │        await self.sell(position, reason='target_profit')        │     ║
║  │        continue                                                  │     ║
║  │                                                                  │     ║
║  │      # 4) 최대 보유 기간 초과 체크                              │     ║
║  │      hold_days = (today - position.entry_date).days             │     ║
║  │      if hold_days >= position.max_hold_days:                    │     ║
║  │        await self.sell(position, reason='max_hold_days')        │     ║
║  │        continue                                                  │     ║
║  │                                                                  │     ║
║  │      # 5) 승격 조건 체크                                        │     ║
║  │      upgrade = self.check_upgrade(position, pnl_pct)           │     ║
║  │      if upgrade:                                                │     ║
║  │        await self.transfer_desk(position, upgrade.new_desk)    │     ║
║  │                                                                  │     ║

║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 2: 청산 실행                                               │     ║

```
## 13. LAYER 7 — Adaptive Engine (학습/진화팀)

```

╠══════════════════════════════════════════════════════════════════════════╣
║                                                                          ║
║  ■ 한 줄 요약                                                           ║

║  │    9~12주: 가중치 0.25                                           │     ║

```
║  │    PricePoller가 유일한 가격 수집기:                            │     ║
║  │      - 한 번만 조회, 캐시에 저장                                │     ║
║  │      - 모든 모듈은 캐시에서 읽기만 함                           │     ║
║  │      - 가격 일관성 보장                                         │     ║
║  │                                                                  │     ║
║  │  ★ V4.1 캐시 구조 (강화):                                      │     ║
║  │    V4.0: price:{ticker} → 가격값                                │     ║
║  │    V4.1: price:{ticker} → {                                     │     ║
║  │      "price": 72500,                                            │     ║
║  │      "ts": "2026-02-13T09:30:15.123",                          │     ║
║  │      "source": "KIS_REST",                                     │     ║
║  │      "staleness_ms": 0                                          │     ║
║  │    }                                                             │     ║
║  │                                                                  │     ║
║  │  왜 staleness가 중요한가:                                       │     ║
║  │    가격이 30초 전 데이터인지 1초 전 데이터인지에 따라           │     ║
║  │    CriticalRiskKernel의 손절 판단이 달라짐.                     │     ║
║  │    stale 가격으로 "안전하다"고 판단하면 위험.                   │     ║
║  │                                                                  │     ║
║  │  ★ V4.1 병렬 수집 + burst 제한:                                 │     ║
║  │    V4.0: for ticker: await get_price() (순차 → 느림)           │     ║
║  │    V4.1: asyncio.gather(*tasks) (병렬 → 빠름)                  │     ║
║  │          + Semaphore(5) (동시 5개 제한 → API 안정성)           │     ║
║  │                                                                  │     ║
║  │  수집 주기:                                                      │     ║
║  │    보유 포지션 종목: 5초 간격 (손절 정확도)                     │     ║
║  │    today_universe 종목: 10초 간격 (진입 타이밍)                 │     ║
║  │    ★ 종목 수가 많으면 API 한도에 맞춰 자동 조절               │     ║
║  │                                                                  │     ║
║  │  수집 우선순위:                                                  │     ║
║  │    EMERGENCY (긴급 청산) > ORDER (주문) > NORMAL (폴링)         │     ║
║  │    긴급 청산이 필요하면 폴링을 잠시 중단하고                    │     ║
║  │    API 한도를 청산에 양보                                        │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 5: KIS API Rate Limiter (V4.1 강화)                       │     ║
║  │                                                                  │     ║
║  │  KIS API 제한:                                                   │     ║
║  │    초당 20회 호출 (하드 리밋)                                   │     ║
║  │    초과 시 IP 차단 가능                                          │     ║
║  │                                                                  │     ║
║  │  class KISRateLimiter:                                           │     ║
║  │    max_per_second: 20        # 초당 최대                        │     ║
║  │    max_concurrent: 5         # ★ V4.1: 동시 요청 제한         │     ║
║  │    semaphore = Semaphore(5)                                     │     ║
║  │                                                                  │     ║
║  │    왜 동시 5개인가:                                              │     ║
║  │      초당 20회가 허용되어도 동시에 20개를 쏘면                  │     ║
║  │      KIS 서버에서 burst로 인식하여 차단할 수 있음.             │     ║
║  │      5개씩 나눠서 보내면 안정적.                                │     ║
║  │                                                                  │     ║
║  │    우선순위 큐 (Phase 5 구현):                                   │     ║
║  │      EMERGENCY 요청이 있으면 NORMAL 요청을 뒤로 미룸            │     ║
║  │      구현: PriorityQueue + Semaphore 조합                       │     ║
║  │      또는 EMERGENCY 전용 슬롯 1개 예약                          │     ║
║  │                                                                  │     ║
║  │  공유 원칙:                                                      │     ║
║  │    PricePoller, Order Executor, fallback 청산이                  │     ║
║  │    모두 같은 RateLimiter 인스턴스를 참조한다.                   │     ║
║  │    "한쪽이 한도를 소진하면 다른 쪽도 대기"                      │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ■ 입력: KIS API, KRX 데이터, DB (과거 데이터)                         ║
║  ■ 출력: 가격 캐시, OHLCV, 수급, 섹터, 지수 데이터                     ║
║  ■ 의존하는 모듈: KIS API, DB                                           ║
║  ■ 의존받는 모듈: 전체 (모든 모듈이 데이터를 소비)                      ║
║  ■ 구현 Phase: Phase 1 (기본) → Phase 4 (병렬+staleness+WebSocket)    ║
║                                                                          ║
╚══════════════════════════════════════════════════════════════════════════╝
```

## 15. INFRA-B — Data Quality Tracker (품질검사관)

```

╠══════════════════════════════════════════════════════════════════════════╣

║    KIS API가 5분 동안 응답 안 하면 5분 전 가격으로 판단하게 됩니다.    ║

║    알려주면 시스템이 자동으로 방어합니다.                                ║
║                                                                          ║
║  ═══════════════════════════════════════════════════════════             ║
║                                                                          ║
║  ■ 세부 역할 분해 (4가지)                                               ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 1: 데이터 소스별 상태 추적                                 │     ║

║  │  data_sources = {                                                │     ║

║  │    },                                                            │     ║
║  │    'kis_order': {                                                │     ║

║  │      ...                                                         │     ║
║  │    },                                                            │     ║
║  │    'krx_supply': {                                               │     ║
║  │      status: 'STALE',         # 10분 이상 갱신 안 됨            │     ║
║  │      last_success: 09:15:00,                                    │     ║
║  │      fail_count: 3,                                              │     ║
║  │    },                                                            │     ║
║  │    'krx_sector': { ... },                                       │     ║

║  │    어느 상태에서든 → LIVE: 성공적 데이터 수신 시              │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║

║  │                                                                  │     ║
║  │  GRADE_A: 모든 소스 LIVE                                        │     ║

║  │    → 로그 경고.                                                 │     ║
║  │                                                                  │     ║
║  │  GRADE_C: 1개 이상 소스 FALLBACK                                │     ║

║                                                                          ║

║  │                                                                  │     ║
║  │  역할 3: 3단계 폴백 (데이터 불가 시 대체)                       │     ║

║  │  1차 (정상): 실시간 데이터                                      │     ║
║  │    → 점수 계산 정상                                              │     ║

║  │    → supply 데이터 DEAD이면:                                    │     ║
║  │      supply_weight(35%)를 나머지 4개에 비례 분배               │     ║
║  │      sector: 20→26%, theme: 15→19%, volume: 15→19%,           │     ║
║  │      tech: 15→19%  (총합 100% 유지)                            │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 4: 품질 이력 기록                                          │     ║
║  │                                                                  │     ║
║  │  매 heartbeat(30초)마다 현재 품질 등급을 기록:                  │     ║
║  │    v4_system_heartbeat에 data_quality_grade 포함               │     ║

║  │  사후 분석:                                                      │     ║

║  │                                                                  │     ║

║                                                                          ║
║  ■ 입력: 각 데이터 소스의 성공/실패 보고                                ║

║                                                                          ║

```

## 16. INFRA-C — Fault Injection (모의훈련팀)

```
╔══════════════════════════════════════════════════════════════════════════╗
║  FAULT INJECTION — 세부 역할 및 기획                                     ║
╠══════════════════════════════════════════════════════════════════════════╣
║                                                                          ║
║  ■ 한 줄 요약                                                           ║

║                                                                          ║
║  ═══════════════════════════════════════════════════════════             ║
║                                                                          ║
║  ■ 왜 필요한가                                                          ║
║                                                                          ║
║    V4.1에서 다양한 장애 대응 로직을 설계했습니다:                      ║
║      - CriticalRiskKernel의 가격 불명 대응                             ║
║      - fallback 청산 경로                                               ║
║      - SELL_FAILED 단계적 재시도                                       ║

║    "장애를 일부러 만들어서" 테스트해야 합니다.                          ║
║    실제 장애는 예측 불가능하고 드물기 때문에                            ║
║    인위적 장애 주입이 유일한 검증 수단입니다.                           ║
║                                                                          ║
║  ═══════════════════════════════════════════════════════════             ║
║                                                                          ║
║  ■ 세부 역할 분해 (2가지)                                               ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 1: 장애 유형별 주입기                                      │     ║
║  │                                                                  │     ║
║  │  환경 변수로 on/off 제어:                                       │     ║
║  │    FAULT_INJECTION=false (기본값, 실거래)                       │     ║
║  │    FAULT_INJECTION=true  (개발/모의 전용)                       │     ║
║  │                                                                  │     ║
║  │  장애 유형 4가지:                                                │     ║
║  │                                                                  │     ║
║  │  [1] FAULT_KIS_TIMEOUT=true                                     │     ║
║  │    동작: KIS API 호출 시 50% 확률로 10초 지연 후 타임아웃      │     ║
║  │    영향: order_executor, price_poller                            │     ║
║  │    테스트 목적:                                                  │     ║
║  │      - 주문 타임아웃 복구 정상 동작?                            │     ║
║  │      - idempotency_key로 중복 주문 차단 동작?                  │     ║
║  │      - 예약금 자동 만료 정상?                                   │     ║
║  │                                                                  │     ║
║  │  [2] FAULT_DB_DELAY=true                                        │     ║
║  │    동작: DB 쿼리 시 30% 확률로 2초 지연 추가                   │     ║
║  │    영향: 모든 DB 의존 모듈                                      │     ║
║  │    테스트 목적:                                                  │     ║
║  │      - 60초 사이클 초과 시 다음 사이클 skip 동작?              │     ║
║  │      - rebuild_from_db가 느려져도 안전한가?                    │     ║
║  │                                                                  │     ║
║  │  [3] FAULT_PRICE_STALE=true                                     │     ║
║  │    동작: PricePoller가 특정 종목(랜덤 1개)의 가격 갱신 중단    │     ║
║  │    영향: CriticalRiskKernel, position_manager                   │     ║
║  │    테스트 목적:                                                  │     ║
║  │      - staleness 60초 초과 시 보수적 청산 실행?                │     ║
║  │      - "가격 불명 = 위험" 원칙이 실제로 작동하는가?           │     ║
║  │                                                                  │     ║
║  │  [4] FAULT_ORDER_REJECT=true                                    │     ║
║  │    동작: KIS 주문 API가 30% 확률로 REJECTED 응답               │     ║
║  │    영향: order_executor, position_manager                        │     ║
║  │    테스트 목적:                                                  │     ║
║  │      - 예약금 FAILED 상태 전환 + 자금 반환 정상?              │     ║
║  │      - SELL_FAILED 단계적 재시도 전략 정상?                    │     ║
║  │      - 지정가→IOC→시장가 전환이 실제 동작?                   │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ┌────────────────────────────────────────────────────────────────┐     ║
║  │                                                                  │     ║
║  │  역할 2: 데코레이터 기반 구현                                    │     ║
║  │                                                                  │     ║
║  │  def fault_injectable(fault_type: str):                         │     ║
║  │    """                                                           │     ║
║  │    FAULT_INJECTION=false이면 완전 no-op (성능 영향 0).          │     ║
║  │    FAULT_INJECTION=true이면 해당 장애 유형의 로직 실행.         │     ║
║  │    """                                                           │     ║
║  │    def decorator(func):                                         │     ║
║  │      @wraps(func)                                                │     ║
║  │      async def wrapper(*args, **kwargs):                        │     ║
║  │        if not FAULT_INJECTION_ENABLED:                          │     ║
║  │          return await func(*args, **kwargs)                     │     ║
║  │                                                                  │     ║
║  │        if fault_type == "KIS_TIMEOUT" and FAULT_KIS_TIMEOUT:   │     ║
║  │          if random.random() < 0.5:                              │     ║
║  │            await asyncio.sleep(10)                              │     ║
║  │            raise TimeoutError("Fault Injected: KIS Timeout")   │     ║
║  │                                                                  │     ║
║  │        if fault_type == "ORDER_REJECT" and FAULT_ORDER_REJECT: │     ║
║  │          if random.random() < 0.3:                              │     ║
║  │            raise KISRejectError("Fault Injected: Order Reject")│     ║
║  │                                                                  │     ║
║  │        return await func(*args, **kwargs)                       │     ║
║  │      return wrapper                                              │     ║
║  │    return decorator                                              │     ║
║  │                                                                  │     ║
║  │  사용 예:                                                        │     ║
║  │    @fault_injectable("KIS_TIMEOUT")                              │     ║
║  │    async def call_kis_api(self, endpoint, params):              │     ║
║  │      return await self.session.post(endpoint, data=params)     │     ║
║  │                                                                  │     ║
║  │  안전장치:                                                       │     ║
║  │    - 실거래 .env 파일에 FAULT_INJECTION=false 고정              │     ║
║  │    - 시스템 시작 시 FAULT_INJECTION=true이면                    │     ║
║  │      "⚠️ FAULT INJECTION 활성 — 실거래 금지" 대형 경고         │     ║
║  │    - KIS 실계좌 키와 FAULT_INJECTION=true 동시 사용 차단       │     ║
║  │                                                                  │     ║
║  └────────────────────────────────────────────────────────────────┘     ║
║                                                                          ║
║  ■ 입력: 환경 변수 (FAULT_INJECTION, FAULT_*)                           ║
║  ■ 출력: 인위적 장애 발생                                               ║
║  ■ 의존하는 모듈: 없음                                                  ║
║  ■ 의존받는 모듈: 없음 (데코레이터로 각 모듈에 삽입)                    ║
║  ■ 구현 Phase: Phase 5                                                  ║
║                                                                          ║
╚══════════════════════════════════════════════════════════════════════════╝
```

## 보고 요약

대표님, 이상으로 V4.1 아키텍처의 **17개 모듈** 각각에 대해 "왜 필요한가 → 무엇을 하는가 → 어떻게 동작하는가 → 다른 모듈과 어떻게 연결되는가"를 상세 기획하여 보고드렸습니다.

핵심 포인트를 정리하면 다음과 같습니다.

**가장 중요한 모듈 3개** (이것이 죽으면 돈을 잃습니다):
Position Manager, CriticalRiskKernel, FundPool. 이 세 가지는 설계에서 "절대 불멸" 원칙이 적용되어 있고, 다른 모듈이 전부 죽어도 이 세 가지만 살아있으면 보유 포지션의 손절은 실행됩니다.

**가장 많은 가치를 만드는 모듈 3개** (이것이 잘 돌면 돈을 법니다):
5 DESK 스코어링, Strategy Engine, Adaptive Engine. 종목 선별의 정확도와 전략 진입 타이밍이 수익의 핵심이고, Adaptive Engine이 이것을 매주 자동으로 개선합니다.

**현재 진행 중인 작업** (Phase 2-B Market Calendar)을 완료하고, Phase 2-C(Command Center)에서 V4.1 핵심 변경 사항들(DB=SoT, ReservationState, idempotency_key, universe 버전화, 레짐 히스테리시스)을 구현하는 것이 다음 마일스톤입니다.
